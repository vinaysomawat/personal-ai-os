A personal, single-user AI Operating System: one Next.js app that tracks tasks, career, money, health, learning, coding practice, and a personal knowledge base — with Claude generating insight in every module, a per-module Telegram bot for hands-free logging (text, voice, or photo), scheduled proactive nudges, and a gamified "Life Score" that rolls all of it into one daily number.

This document describes exactly what the app does today, module by module, field by field, formula by formula, so it can be pasted into a fresh AI chat and give that AI complete understanding of the system with no other context needed. It is kept current with every functional change (see `CLAUDE.md`'s post-task checklist).

**Status:** this is a personal project built for one person's specific life and workflow — not a product, and not designed for multi-tenant use. It's open-sourced as a working example of an AI-assisted personal system (Next.js + Supabase + Claude + Telegram), not as a tool meant to be deployed as-is for someone else's life. Fork it, borrow the patterns you like, adapt the modules you don't need.

To run your own instance: clone the repo, `npm install`, copy `.env.example` to `.env.local` and fill in your own Supabase project / Anthropic key / Telegram bot tokens (see [Environment variables](#environment-variables)), run the SQL files in `supabase/migrations/` against your Supabase project in order, then `npm run dev`. ## 1. Dashboard (`/dashboard`)

The home screen. Server-computed on every load (`src/features/dashboard/actions.ts`):

- **Life Score (0–100)** (v2, 2026-08-23) — every module score is a blend of two numbers, not one, so it actually responds to what you log instead of just what you touched:
  `moduleScore_M = dailyRaw_M × 0.6 + weeklyAvg_M × 0.4` (weights in `LIFE_SCORE_THRESHOLDS.dailyWeight`/`.weeklyWeight`, `src/lib/thresholds.ts`), then
  `lifeScore = round(Σ moduleScore_M × categoryWeight_M)` with the category weights unchanged: `health×0.25 + finance×0.20 + career×0.20 + learning×0.20 + projects×0.15`.
  - **Why a blend, not a pure daily snapshot or a pure weekly average**: a pure daily score (v1) meant a module could sit at a misleadingly high number forever just because something was *logged* that day, regardless of whether the logged value was actually good — the exact bug that prompted this rewrite (eating well over a fat-loss calorie target didn't move the score, because v1's Health score only checked presence, not accuracy). A pure weekly average would remove all same-day feedback — nothing you do today would move the ring until tomorrow. The 60/40 blend keeps today's real effort visibly moving the number the same day, while the 40% weekly component stops one lucky day from fully erasing a bad week or one bad day from tanking a genuinely strong one.
  - **`dailyRaw_M`** — today's fresh, quality-aware snapshot, judged against a real target where one exists (see the 5 formulas below). This is the only figure ever persisted to `life_score_logs` per module — **never the blended figure**, since storing a blend would make tomorrow's weekly average partly an average of an average, compounding every day into an effectively unmovable number. `lifeScore` itself is the one exception: it's stored already-blended, since nothing ever averages `life_score` back into a future computation (only the 5 per-module raw scores feed the weekly averages).
  - **`weeklyAvg_M`** — the mean of that same raw score over the trailing 7 days including today, computed at read time from `scoreHistory` (already fetched, no new query). A day in that window with no `life_score_logs` row at all (app wasn't opened, so nothing was ever computed) counts as **0**, not excluded from the average — otherwise skipping the app on a bad day would let someone game the weekly number. Exception: an account less than 7 days old averages only over the days that exist since signup (`user.created_at`), so a brand-new account's first week isn't crushed toward 0 by pre-signup days.
  - **Health score** — reuses the Health module's own quality-aware `calculateHealthScore()` (§5: `nutrition×0.6 + activity×0.4`, checked against real BMR/TDEE-derived calorie/protein/step targets) instead of a separate presence-only formula, so eating well over a real calorie target now genuinely drops the score. Falls back to the old presence-only formula — `(anyWorkoutLoggedToday ? 60 : 0) + (metricsLoggedToday out of 4 fields / 4) × 40` — only when no `health_profile` exists yet (targets uncomputable).
  - **Finance score** — same band shape as before, smoothed within each band instead of a hard cliff: `ratio≤0.70→100`, `ratio≤0.85→linear 90→75`, `ratio≤1.00→linear 75→55`, `ratio≤1.20→linear 55→30`, else `max(10, 30−(ratio−1.20)×40)`; `60` if no budget set and zero spend logged, `50` neutral default otherwise. (v1's cliff meant crossing 90% of budget by even ₹1 cost 15 points outright.)
  - **Career score**: `min(100, (profile filled?15:0) + min(20, skills×2) + min(25, activeApplications×8) + min(20, quizAttemptsLast30Days×4) + (jobAlertTrackedLast30Days?20:0))` — recurring signals replace v1's static one-time fillers: a quiz taken once used to permanently max that clause forever; now it's quiz attempts in the trailing 30 days. New clause: tracking a Job Alert (§3) into an application in the last 30 days.
  - **Learning score** (changed 2026-09-24): `min(100, round(completedLast30d / LIFE_SCORE_THRESHOLDS.learningCompletionsTarget (20) × 100))`, where `completedLast30d` counts resources with `completed_at` in the last 30 days — a habit signal, replacing v1's `(completed + in-progress×0.5) / total` backlog ratio (which moved when unread items were deleted, not when anything was read). `resources.completed_at` (timestamptz, 2026-09-24 migration) is stamped on every transition to `completed` — web status change, Planner task toggle, Telegram complete/progress-100/Done button — and cleared on leaving it; pre-existing completed rows were backfilled with `created_at` as an approximation.
  - **Projects/Coding score** (changed 2026-09-24): `round(volume × 0.5 + consistency × 0.5)`. **Volume** = `min(100, round(weightedCompletions × 3.2))`, `weightedCompletions = Σ` `coding_daily_questions` completed in the last 30 days, each weighted by category (`LIFE_SCORE_THRESHOLDS.codingCategoryWeight`: algorithm `1.0`, system-design `1.5`, quiz/javascript-functions/ui-coding `0.6`). **Consistency** = `min(100, round(practiceDays / codingPracticeDaysTarget (20) × 100))`, practice days = distinct IST days with a completion. Both key on `completed_at`, not `assigned_date` — the old assigned-date/volume-only formula let a 37-question bulk catch-up of August picks hold the score at 96–100 through a September with 6 practice days. Tip names the practice-day count when consistency is the weaker half. Reuses `codingHistoryForWeakAreas` — no new query.
  - Every dashboard load **upserts today's raw sub-scores + the blended `life_score`** into `life_score_logs` (one row per user per day)
  - **Explain My Score** — clicking the Life Score ring opens a popover (`src/features/brain/components/ScoreExplainer.tsx`) showing each module's full breakdown — `"{today} today · {weeklyAvg} this week avg → {blended}"` — plus a day-over-day delta of the *blended* figure (computed by also blending yesterday's raw score with its own trailing 7 days, not by diffing raw-vs-blended) and that module's existing deterministic tip, sorted biggest movers first. Fully deterministic — no AI call. `explainScore()` (`src/features/brain/calculations.ts`) is now a thin sort/label layer — all the blending math lives in `getDashboardData()`, which passes a finished `scoreBreakdown: Record<ScoreModule, {today, weeklyAvg, blended, delta}>` in.
  - **Life Score Trend** (`LifeScoreTrend.tsx`, lazy-loaded via `next/dynamic` with `ssr: false` — recharts is a ~100KB client-only dependency used nowhere else in the app, so it's code-split out of the main bundle rather than block initial paint) — a Weekly/Monthly-toggle line chart of the Life Score, fed entirely by `scoreHistory` (30 days of `life_score_logs`, already fetched for Explain My Score above — Weekly is just its last 7 points, no new query). Its `life` line is the blended headline trend (smoother by design); the per-module lines elsewhere that read the same `scoreHistory` stay raw/spikier, since only `life_score` is stored already-blended. Deterministic, no AI.

Read-only pointer, not dismissible — dismissing stays exclusive to the full Needs Attention card.

  - **What's Changed** (`WhatsChanged.tsx` + `whats-changed.ts`) — pure deterministic day-over-day deltas, no AI: Life Score Δ (vs. yesterday's `life_score_logs` row), weight Δ, a new expense/workout/application logged today. Each links to its module. On a day with nothing to show, renders as one slim inline line (no `Card` title/padding chrome) rather than a full-width card holding a single throwaway sentence.
  - **Morning Brief** (`ExecutiveBrief.tsx`) — the AI paragraph from the `daily-briefing` cron (§11), persisted to `daily_briefings` (`upsert(onConflict: user_id,date)`) so the Dashboard shows it without a fresh AI call on every page load. Shows a plain "not generated yet" state before that morning's ~8:30am IST cron has run, rather than triggering one live. Below a divider (added 2026-08-18, per the Claude Design source): a compact "Automation Rule" / "Risk" / "Opportunity" highlights strip — the single top item from each of `computeAutomationRules()`/`computeRiskEngine()`/`computeOpportunityEngine()` (`getExecutiveData()` in `executive-actions.ts`, same already-fetched deterministic data Needs Attention renders in full below), not a new query or AI call.
  - **Needs Attention** (`NeedsAttention.tsx`) — replaces the old separate "Today's Focus" card and Executive Brief's "Decision Queue," consolidated into one ranked list capped at 3 ("anything more indicates prioritization failed," per the PRD) rather than showing the same class of information across multiple cards. Row style restyled 2026-08-18 to match the Claude Design source: a uniform colored dot per row (risk keeps its real per-severity color — red/amber/yellow — rather than the design's flattened single red) replaces the old per-type icon/emoji, and risk/opportunity rows show a second "→ {action}" suggestion line — `Opportunity` gained an `action` field split out from its one-sentence text to match `Risk`'s existing shape. Risk/Opportunity items link to their module (`KIND_HREF` in `dashboard/priority.ts` maps each risk/opportunity `kind` — `budget_pace`→Finance, `protein_decline`→Health, `coding_streak`→Coding, `interview_momentum`→Career) and keep the same dismiss mechanism as before (`decision_queue_dismissals`, `useOptimistic`); signal items are plain links, not dismissible.

Falls back to a plain "no confirmed pattern yet" message.

A separate on-demand AI narrative from Daily Auto Journal's 11pm cron (different purpose: this is a same-evening check-in, that's an end-of-day recap needing to run after even a late coding session) — reuses the journal's activity-gathering (`gatherTodayActivityLines()`, a shared helper). Routes through the gateway as `evening_reflection` (Sonnet, 6h cache). Fetched only after the time gate passes, so it never blocks initial page load. **"Tomorrow's top priority" is a separate deterministic line, not part of the AI narrative** (changed 2026-08-18, per the Claude Design source) — `generateEveningReflection()` picks the single highest-priority pending Planner task (same overdue-first/priority-rank sort the Dashboard's own Top Priority banner uses, Product Principle 2) and returns it as its own `tomorrowsPriority` field; the AI's system prompt was updated to explicitly *not* mention tomorrow's plans, since the pick is shown as its own 🎯-prefixed line below a divider instead of woven into prose (previously the AI was asked to close its paragraph naming this same pre-computed task — moving it out removes any risk of the AI paraphrasing/altering the task text, and the reflection's cache key no longer needlessly busts on unrelated pending-task priority churn).

## 2. Planner (`/planner`)

Simple task list. Fields: `text`, `done`, `priority` (high/medium/low), `area` (free text, defaults "General"), `due_date`, `recurrence` (daily/weekly/monthly or none).

- Add / delete / toggle-done; no manual priority-edit or sort UI (the old "AI Sort" feature — which was actually deterministic, not AI — was removed entirely per user request; tasks render in creation order, pending then completed)
- **Clear Completed** (added 2026-09-01) — a "Clear Completed" link inside the collapsed Completed section bulk-deletes every completed task in one confirm, rather than requiring one delete-and-confirm per row (impractical once completed count reaches the hundreds). `deleteCompletedTasks()` (`planner/actions.ts`) is a single `delete().eq('done', true)`, scoped by RLS same as every other table write; Coding/Health/Learning's own linked rows (`coding_daily_questions`/`daily_workouts`/`resources.task_id`) use `on delete set null`, so bulk-clearing can't leave a dangling FK — those rows just lose their task link, same as deleting one task at a time already did.
- **Stats row** (Pending / High Priority / Overdue / Completed) above the task list, and a **By Area** panel beside it on wide viewports (`lg:` breakpoint, task list `lg:col-span-3` / right column `lg:col-span-2`) — deterministic counts grouping pending tasks by their `area` field, no AI
- **Pending Tasks by Day** (added 2026-08-18, per the Claude Design source) — a small bar chart stacked below By Area in the same right column, showing the **cumulative pending-task backlog by day** (changed 2026-08-24, was a per-weekday-name histogram that reset every week, e.g. "every Wednesday ever" rather than actual dates). X-axis is the last 7 real calendar days (labeled e.g. "Tue 1", not just a weekday name); each bar is the running total of currently-pending tasks created on or before that day, so the chart reads as "how did today's backlog build up." Deterministic, client-side from the same already-fetched pending-tasks list, no new query. Not a true historical reconstruction — tasks have no `completed_at`, so a task completed since day D can't be added back into that day's count — but the closest achievable proxy with existing data. Bucketed by `created_at`, not `due_date` — the web Add Task form has no due-date field at all (only the Telegram bot's `add_task` sets one) and there's no task-edit UI anywhere in the app to add one retroactively, so grouping by `due_date` left this chart empty for virtually every task; `created_at` is always populated.
- **Month-scoped Today's Tasks + Overdue**: a task's "relevant month" is its `due_date`'s month if set, else the month it was `created_at` in (most tasks have no `due_date`, so this is effectively "the month it was added"). Today's Tasks only shows tasks whose relevant month is the current month or later; anything left incomplete from a prior month surfaces in a separate, always-visible **Overdue** card instead of lingering in the main list or silently disappearing. Both lists cap at 480px tall and scroll internally past that, so a long backlog doesn't push the rest of the page down.

## 4. Finance (`/finance`)

The richest module — full personal finance tracking, scoped to the **current calendar month** for expenses/budgets:

- **Expenses** — `amount`, `category` (Food/Transport/Housing/Health/Shopping/Entertainment/Learning/Utilities/EMIs/Bills/Family/Travel/Other — Family and Travel added 2026-09-24 after a usage audit found ~35% of August spend filed under Other, mostly money given to relatives; the Finance bot's parse rules route "given to X"/gifts → Family and trips → Travel. Existing Other rows were not recategorized), `description`, `date`. Add / delete. (`recurring_expense_id` was dropped 2026-08-20 along with Recurring Expenses itself — see below.)
- **Budgets** — one amount per category per month (`upsert` on `user_id,category,month`). **Carried forward automatically**: when `getFinanceData()` loads a month where a category has no budget row yet, it looks up that category's most recent prior-month amount and upserts it into the current month — a new month never starts blank. "Removing" a budget (the By Category editor's Remove button) sets the amount to 0 rather than deleting the row, specifically so it stays carried-forward-as-0 instead of a later month resurrecting an older nonzero amount.
- **Spending History** — a card below Payment Calendar, fed by one extra query in `getFinanceData()` (last 12 months of `expenses`, grouped client-side, deterministic/no AI): a bar chart of total spend per month (click a bar, or the prev/next arrows, to change the selected month) and a pie chart of that month's spend-by-category, using the same category color mapping as "By Category"/"Expenses". Charts are `recharts` (already a dependency, zero new package), lazy-loaded via `next/dynamic({ ssr: false })` the same way Dashboard's Life Score Trend is. Note: `<Pie isAnimationActive={false}>` is required — recharts 3's default Pie entry animation never resolves under this lazy-mount setup (sectors exist in the DOM but never paint), a gotcha specific to Pie (Bar/Line charts elsewhere in the app aren't affected).
- **Finance profile** — `monthly_salary`, `emergency_fund_months`. Changing salary auto-appends a row to `salary_history` (`amount`, `effective_date`, `note`) so raises are tracked over time.
- **Loans** — `name`, `principal`, `emi`, `interest_rate`, `remaining_months`, all **inline-editable** (EMI/rate/remaining-months can be updated in place without delete+recreate). **Total Debt = outstanding principal** (`loanOutstanding()` in `src/features/finance/calculations.ts`): the present value of the remaining EMIs at the loan's rate, `emi × (1 − (1+r)^−n) / r` with `r = rate/12/100` — falling back to `emi × months` when no rate is set. Changed 2026-09-24: the old `Σ emi × remaining_months` included every future interest payment (~₹9.8L overstated on the home loan, understating Net Worth by the same). That interest-inclusive figure is still shown as a sub-line ("₹X payable incl. interest", `loanTotalPayable()`). The same helper feeds the Money Advisor context and the Telegram `net_worth` reply, so all three surfaces agree. Each loan row also shows a sub-line "₹X owed · N% of ₹principal repaid · ends Mon YYYY" with a thin green repaid bar (`1 − outstanding/principal`; payoff month = current month + `remaining_months` − 1 via `loanPayoffMonth()`). **Months left auto-decrement** (2026-09-24): `remaining_months` is stored together with `remaining_months_as_of` (the 1st of the month it was set — written on every add/edit, web or Telegram), and the live count is derived at read time by `loanEffectiveRemainingMonths()` as `max(0, stored − calendar months since as_of)`, ticking down on the 1st of each month (not the actual EMI debit day — no such field). Derived rather than cron-rewritten, so a missed job can't skip a month. `getFinanceData()` normalizes loans through it once, so the page, the inline editor (which shows and re-saves the effective count), and the Money Advisor all read the current value; the Telegram `net_worth`/`ask` handlers apply it to their own queries.
- **Investments** — `name`, `type` (mutual_fund/stocks/fd/crypto/other), `invested_amount`, `current_value` (both inline-editable), `notes`. P&L = current − invested. `current_value` is manually edited (no market/NAV data source exists in the app). Rendered as one flat list, sorted by current value descending (was insertion order until 2026-09-24), name in bold primary text, gain shown as `(±₹X · ±Y.Y%)` return on invested, each row in a `surface-2` pill (added 2026-08-18, matching the Claude Design source — the pill was previously missing, rows rendered as plain unwrapped text). **(SIP tracking — auto-monthly-contribution mode, its own cron, and the SIPs/Lump Sum UI split — was removed 2026-08-10.** `is_sip`/`sip_amount`/`sip_day_of_month`/`sip_last_contribution_month` were dropped from `investments` in a 2026-08-20 schema-debt cleanup migration — any pre-existing SIP rows now just behave as plain investments. See §11's cron table.)
- **Recurring Expenses — removed entirely (2026-08-20)** per direct request ("remove recurring expenses from finance, and clean up the code"). The `recurring_expenses` table, its daily cron, `expenses.recurring_expense_id`, the add/toggle/delete server actions, the UI card, and the Finance Telegram bot's `add_recurring`/`list_recurring` commands are all gone — no orphaned schema was left behind for this one (unlike some other removed features), since the migration also dropped the column/table outright.
- **Payment Calendar** (2026-08-18, redesigned 2026-08-20 — `computePaymentCalendar()` in `actions.ts`, `PaymentCalendar.tsx`) — now a plain day-by-day expense log, no longer driven by recurring due-dates at all: a GitHub-style heatmap where each day is either **Logged** (green, ≥1 `expenses` row that date) or **None** (dashed outline, no expenses that date) — 2 states, not the old 4 (Paid/Pending/Missed/blank). No streak/active-rate framing (unlike Coding/Learning/Health's calendars) — spending isn't a habit worth a streak, so a "None" day isn't a miss. Stats shown: total spent this month, % of days with an expense logged, and a logged-vs-none day count. Prev/next month nav, click any day to see that day's actual logged expenses (description/category/amount) or "No expenses logged this day." Stands alone, full-width, directly above Spending History (previously paired side-by-side with Recurring Expenses).
- **Financial goals** — `name`, `target_amount`, `current_amount`, `target_date`, `priority`. Add / update progress / set target date inline (`updateGoalTargetDate()`, 2026-09-24 — previously only settable at creation) / delete. With a target date, the row shows "By Mon YYYY · ₹X/mo needed" (`goalMonthlyNeeded()`: remaining gap ÷ calendar months left incl. the current one, min 1); without one, a "+ Set target date" link.
- **EMI is not double-counted**: `loans.emi` is purely informational (shown only in the "Total Debt" card) and is never added on top of logged expenses — if EMI is paid, it's expected to already appear as a regular (typically "Bills") expense, and spend totals reflect only actual logged `expenses` rows.
- **Month pace** (2026-09-24, `projectMonthSpend()` in `calculations.ts`, shared with the Risk Engine's `budget_pace` check so both report the same projection): fixed monthly categories (`FIXED_MONTHLY_CATEGORIES` = EMIs) count once as-is, everything else is extrapolated at this month's per-day rate — a lump EMI debit is never multiplied across the month. Drives the By Category stats row (Month-end pace, and ₹/day left = non-EMI budget remaining ÷ days left incl. today) and the header's "On pace to save X% of salary" chip (`(salary − projected) / salary`, percentage only so the masked salary isn't revealed).
- **Budget suggestions** (2026-09-24, `suggestBudgets()`): per-category average over the last 3 *complete* calendar months (current month excluded, divided only by months that have any expense), rounded up to ₹500, computed from the already-fetched 12-month `expenseHistory` — no extra query, no AI. By Category shows a "Suggest budgets from 3-mo avg (N)" link only when some suggestion differs from the current budget; it opens an inline current → suggested review list with Apply all (`upsertBudgets()`, one batch upsert) / Cancel.
- **Over-budget banner**: lists every over-budget category, worst overage first (top 3, then "+N more"), ignoring overages under `FINANCE_THRESHOLDS.overBudgetBannerMinRatio` (2%) of that category's budget — an EMI running ₹420 over a ₹35,000 budget used to trigger the banner every month. The row's own Over / At limit badge still shows small overages.
- **By Category drill-down**: each category row in the "By Category" breakdown is clickable — expanding it lists every individual expense logged in that category this month (date, description, amount, delete), not just the aggregate spent total.
- **Rolling 3-month average expense** — computed on every load from the last 90 days of expenses, used as the "realistic monthly spend" baseline (as opposed to just this month's partial total).
- **Money Advisor** (`finance-advisor.ts`) — opened from the header trigger (see "AI advisor header architecture" under Architecture), two tabs:
  - **Ask** — free-form Q&A fed the full financial snapshot: salary, EMIs (itemized per loan), 3-month avg spend, free cash/month (`salary − avgMonthlyExpense`, where `avgMonthlyExpense` already includes logged EMI payments — not a separate `salary − EMIs − avg spend` subtraction, that would double-count), portfolio with per-holding P&L, goals with target dates, and emergency-fund target in ₹. Answers under 200 words, numbers-driven. Quick-prompt chips for common questions.
  - **Simulate** (`ScenarioSimulator.tsx`, Phase 4 PRD's Scenario Simulation) — a structured form (total cost, paid upfront, EMI amount, EMI duration), not free text, so every number in the result is exactly what was typed rather than an AI guess at a purchase's down-payment/EMI split. `computePurchaseScenario()` (`src/features/finance/scenario-simulation.ts`) is pure deterministic math (Product Principle 2 — AI never computes the numbers): `freeCashAfter = freeCashBefore − emiAmount`, plus a "months to reach it if all new free cash went there" estimate per unfunded goal, explicitly caveated as a simplification (goals aren't individually funded/tracked, only a target/current snapshot exists) rather than a real forecast. Scoped to cash-flow impact only — no modeling of which savings pool a down payment draws from, since no field distinguishes that and guessing would mean inventing an assumption. `narratePurchaseScenario()` (`finance_scenario` task, Sonnet, uncached) then writes a short verdict from only the already-computed numbers, under 150 words.

- **Calculations** (`calculations.ts`, pure functions, no AI):
  - **BMI** = `weightKg / (heightCm/100)²`
  - **BMR** (Mifflin-St Jeor): `10×weightKg + 6.25×heightCm − 5×age`, `+5` for male / `−161` for female
  - **TDEE** = `BMR × activity multiplier` (`sedentary 1.2, light 1.375, moderate 1.55, active 1.725, very_active 1.9`)
  - **Normal-BMI target weight** = `24.9 × (heightCm/100)²` (upper bound of the normal BMI range — the most achievable target for someone starting overweight, auto-computed from height, no manual entry)
  - **Daily targets** (`calculateDailyTargets`): if current weight puts BMI above 24.9, calorie target carries a modest deficit (`0.4–1kg/week`, scaled to how much is left to lose) toward the normal-BMI weight; otherwise it's maintenance. `dailyCalorieTarget = max(1500, round(TDEE − deficit))`. **Protein target is based on the normal-BMI target weight while cutting, not current scale weight** (`2g × targetWeightKg`) — standard fat-loss guidance, since 2g/kg of an overweight starting weight overshoots real need. Fat = `25% of calorie target ÷ 9`, carbs = remainder `÷ 4`.
  - **Health Score (0–100)**: `nutrition×0.6 + activity×0.4` — nutrition blends calorie-accuracy and protein-hit-rate 50/50 (0 if nothing logged); activity blends step-target-% with a workout-today bonus/floor. Each sub-score carries a plain-English reason naming whichever factor is actually worse that day (changed 2026-08-20 — nutrition's reason used to always name the protein gap regardless of which one was further off, since protein's target is high enough that its gap was almost always >20g and permanently won; now it compares `calScore`/`proteinScore` directly and shows the lower one's issue, e.g. "Calories are 63% off target" surfaces correctly when that's the bigger miss). No sleep component (removed).
- **Weight Trend** (2026-09-24, `WeightTrendCard.tsx` + `computeWeightTrend()` in `calculations.ts`) — replaces the old README claim of a `HealthTrend.tsx` chart, which no longer exists in the code. Hover/tap shows date + value with a crosshair. Needs ≥3 weigh-ins spanning ≥7 days, otherwise a prompt. Deterministic, no AI.
- **Activity-level check** (2026-09-24, `suggestActivityLevel()` in `calculations.ts`) — compares the profile's `activity_level` (which drives TDEE, hence the calorie target) against the last 28 days of real data: workout days/week from the Workout Calendar (the `workouts` table) and average steps over logged days (needs ≥7), banded the same way `ACTIVITY_LEVELS`' labels describe (light 1-3 days/week, moderate 3-5, active 6+), bumped one level at ≥10k avg steps. (The Difficulty Progression trend chart that used to sit below the Calendar was removed from the page along with `computeDifficultyProgression()`/`DifficultyProgression.tsx` — nothing else referenced either, so both were deleted outright rather than left as dead code.)
- **Recommended for You** (on-demand, "Get Recommendations" button, not auto-run) — `getCodingRecommendations()` (`coding/recommendations.ts`) deterministically narrows the pool first (topic overlap with weak areas and/or an active application's Career JD analysis priority topics — Product Principle 4, gracefully falls back to any not-yet-attempted topic-tagged question when there's no signal yet), then `recommendCodingQuestions()` (`ai/coding-mentor.ts`, `askAI('recommend_coding_questions', ...)`, Sonnet, never cached) has Claude pick and rank the best 3-5 from that already-narrowed candidate list using its knowledge of current interview trends — "quality over quantity." **Never invents a question** — the model can only return an id that was in the candidate list it was given (enforced by filtering the response against the actual candidate ids, not just prompted), mirroring Learning's and Career's own anti-hallucination stance. "+ Add" on a pick calls `addRecommendedQuestion()`, which mirrors the daily-assignment insert logic (creates the linked Planner task + `coding_daily_questions` row) for that one specific question. Before the 2026-08-18 topic backfill, quiz/system-design rows never surfaced here since they had no `topics` to match against; now that every category has topics, any category is a structurally eligible candidate — this widget was never algorithm-specific by design, it was only ever gated by which rows happened to have topics populated.

## 10. Telegram bot — the interaction layer

Each module is its own Telegram bot (own `TELEGRAM_BOT_TOKEN_*`), all pointed at one webhook (`src/app/api/telegram/[module]/route.ts` → `src/features/telegram/handler.ts`).

**Processing pipeline:**

1. Only messages from `TELEGRAM_ALLOWED_CHAT_ID` are accepted (single-user, single-chat system).
2. A daily AI-call cap (`TELEGRAM_DAILY_AI_CAP`, default 300) counted from `telegram_logs` protects against runaway spend — once hit, the bot replies with a quota message and skips processing entirely for the rest of the day. Separately, the Gateway's own dollar budget (§12) reserves a slice of the daily *and* monthly spend exclusively for `telegram_intent`/`telegram_vision` — if that reserve check fails, the handler replies `⏸️ AI budget for today is used up — resets at midnight IST` (daily ceiling) or `⏸️ AI budget for this month is used up — resets on the 1st` (monthly ceiling, worded separately since it doesn't reset tonight) and logs `{"action":"budget_exhausted","scope":"daily"|"monthly"}`, distinct from the `{"action":"help"}` cheat-sheet reply below (added 2026-09-23 after a `recommend_daily_read` web-search call alone exhausted a full day's budget and every bot silently fell back to the help menu, indistinguishable from a real parsing miss).
3. **Voice messages** are transcribed first via Groq's `whisper-large-v3-turbo` (needs `GROQ_API_KEY`) before anything else happens.
4. **Photos** are supported by Finance (receipt → extracts amount + category) and Health (meal photo → estimates calories + protein) via a per-module `VISION_PROMPT`; other bots reply that photos aren't supported yet.
5. The transcribed/typed text (or image) goes to Claude with a module-specific system prompt defining a JSON action grammar, plus the actual current date injected (so "today" never relies on the model's training cutoff). A single message can produce **multiple actions** (e.g. a voice note describing a workout, water, and a finished chapter all at once) — the model returns a JSON array instead of one object, and each is executed and replied to in turn.
6. Claude's response is parsed and dispatched to that module's `execute()`, which does the real Supabase read/write and formats a Markdown reply.
7. Every interaction (module, chat id, message, parsed action(s), reply) is logged to `telegram_logs`, non-fatal on logging failure.

**Cross-cutting bot features:**

- **Undo/amend**: every bot supports `undo_last` (deletes/reverts the most recent write for that module — task, expense, application, ad-hoc workout log, resource, or coding-question/reading completion); Finance additionally supports `amend_expense` (corrects just the amount on the most recent expense).
- **Reminders**: Planner can `set_reminder`/`list_reminders`/`delete_reminder` (writes the `reminders` table used by Settings, §9).
- **Inline buttons**: adding a task attaches a "✅ Mark Done" button; tapping it completes the task (and syncs Coding's daily question or a Learning resource if linked) without going through the AI layer at all. Every "add" action across 5 of the 7 bots — Planner, Career, Finance, Health, Learning (task, application, expense, loan, investment, ad-hoc workout log, learning resource) — also attaches an "↩️ Undo" button (`src/lib/telegram/buttons.ts`); Coding and Astrology don't attach one (Coding's `complete_question`/`undo_last` and Astrology's read-mostly command set have no equivalent "add" action to undo). Unlike the `undo_last` text command, which always targets the most-recently-created row, the button encodes the specific row's id in its `callback_data`, so tapping it later (after newer items were added) still undoes the correct one, not whatever's newest at tap time. An explicit table allowlist (`UNDOABLE_TABLES`) guards the generic `undo:<table>:<id>` callback handler in `handler.ts` against acting on an unexpected table.
- **Proactive budget nudge**: logging an expense via Finance checks that category's budget and appends a warning if it's now over or ≥90% used.

## 12. AI Gateway

Every AI call in the app funnels through one function: `askAI(task, prompt, system?, opts?)` in `src/lib/ai-gateway.ts`. No feature module calls Anthropic directly (`src/lib/anthropic.ts`'s `callClaude()` is a low-level primitive only the gateway imports). This is Product Principle 3 made concrete. `askAIWithMeta()` (added 2026-08-20) is the same gateway logic returning `{text, generatedAt}` instead of a bare string — `askAI()` is just a one-line wrapper around it that discards `generatedAt`, so every pre-existing call site is unaffected. Only the 3 call sites that display a freshness timestamp on cached AI content (Career's Recommended Topic and Interview Guidance, §3; Astrology's Characteristics, §13) use the `WithMeta` variant directly.

- **Model routing** — a fixed per-task table picks the model. Only `telegram_intent` routes to Haiku (`claude-haiku-4-5`); every other task (`telegram_vision`, `career_mentor`, `jd_analysis`, `generate_topic_quiz`, `recommend_quiz_topic`, `company_insights`, `finance_advisor`, `health_report`, `health_daily_plan`, `health_advisor`, `study_plan`, `resource_quiz`, `recommend_resources`, `recommend_daily_read`, `coding_mentor`, `recommend_coding_questions`, `module_recommendations`, `daily_briefing`, `weekly_digest`, `monthly_digest`, `brain_qa`, `brain_decision`, `brain_weekly_reflection`, `brain_monthly_review`, `daily_journal`, `finance_scenario`, `evening_reflection`, `estimate_food_nutrition`, `astrology_reading`, `astrology_characteristics`) routes to Sonnet (`claude-sonnet-4-6`). (`doc_qa`/`doc_summary` were removed with the Documents module, §8 — no longer real tasks.)
- **Response caching** — `ai_cache` table, key = `sha256(model::system::prompt)`. A changed prompt (i.e. changed underlying data) naturally busts the cache. Per-task TTLs range from none (always fresh, e.g. Q&A/decision/scenario tasks whose prompt genuinely differs per call) up to a full year (`astrology_characteristics` — effectively permanent, since its prompt only changes when the natal chart itself does, §13); `company_insights`/`estimate_food_nutrition` use 7 days (nutrition facts for the same item+quantity don't change, so a repeat like "200g chicken breast" is a cache hit); images are never cached. A cache hit skips the API call entirely and logs zero cost. Per CLAUDE.md's "minimize Anthropic API usage" guidance, every cron-generated narrative/digest task (`daily_briefing`, `weekly_digest`, `monthly_digest`, `daily_journal`) uses a 6h TTL rather than none — most have an on-demand Telegram duplicate (e.g. "how am I doing" re-running `daily_briefing` the same morning the cron already sent it) that would otherwise re-spend an API call for byte-identical output. **`astrology_reading` is the one task whose TTL isn't a fixed `TASK_CONFIG` constant** — `askAI`'s `opts.cacheTTLSeconds` can override the task's default per call, and `astrology/actions.ts` computes it dynamically per request: seconds until the next IST midnight for `daily`, until the 1st of next month for `monthly`, until next Jan 1 for `yearly` — so a reading caches until its own calendar period actually ends, not a flat duration, and a repeat request (web reload, or the Telegram bot/cron's own same-day call) costs zero extra spend for the rest of that period.
- **Budget enforcement** — `ai_usage_logs` logs every call (task, model, tokens, `estimated_cost_usd`, cache-hit flag). Before calling the model, the gateway sums today's and this month's spend (fail-open on a spend-lookup error itself — treated as $0 spent rather than throwing, so a transient DB blip can't block every AI call in the app); if either meets `AI_DAILY_BUDGET_USD` (default $3) or `AI_MONTHLY_BUDGET_USD` (default $50) — scaled down for non-interactive tasks, see the reserve below — it skips the API call and returns that task's configured fallback string instead. `askAI()` also wraps the actual API call itself in a try/catch (`ai-gateway.ts`) — **any** failure (budget, API error, network) returns the same configured fallback rather than throwing, so no page or cron job can ever break from an AI call failing; structured-output tasks fall back to `'[]'`/`'{}'`/`'{"action":"help"}'` for silent degradation, a few user-facing Q&A tasks (`career_mentor`, `finance_advisor`, `health_advisor`, `coding_mentor`, `brain_qa`, `finance_scenario`) return an explicit "I'm over my AI budget for today" message, and every "always send" cron-generated narrative (`daily_briefing`, `weekly_digest`, `monthly_digest`, `daily_journal`, `evening_reflection`) has an explicit one-line "AI summary/reflection/journal unavailable" fallback (changed 2026-08-20, was an empty string — a real Sonnet failure on one of these used to silently leave a blank gap in an otherwise-fine message rather than saying anything). **Interactive-task reserve** (added 2026-09-23): `telegram_intent`/`telegram_vision` are checked against the full daily *and* monthly budget, but every other task is checked against only 70% of each (`INTERACTIVE_RESERVE_FRACTION`) — so a background cron/on-demand task spending unevenly earlier in the day, or across the month, can use up to that 70% before it starts getting blocked, but can never fully starve someone actively texting a bot. `askAIWithMeta()`'s result also now carries `budgetExhausted` plus which ceiling actually tripped (`budgetScope: 'daily' | 'monthly'`) so a caller (the Telegram handler) can tell "budget ceiling hit" apart from "missing userId" or "API error" (which all previously collapsed into the same fallback string with no way to distinguish them), and can word its message correctly — a monthly cutoff resets on the 1st, not at midnight, so the handler shows a different reply for each scope instead of one `{"action":"help"}` cheat-sheet or a message that wrongly promises the bot is back by midnight. No task grants Claude the server-side `web_search` tool (removed 2026-09-23 along with the `AskAIOptions.webSearchMaxUses`/`callClaude` plumbing that enabled it — a single search call had been observed returning 80k+ input tokens, enough alone to blow a day's budget, with no way to cap how much a search returns, only how many run); every task that used to verify a URL via search (`recommend_daily_read`, `recommend_resources`) now has the model self-report instead, null when unsure.
- **Rule-engine-first**: score math, sorting, chart data, the coding rotation, and the daily-read pick (curated-pool tier of it, at least — the AI-fallback tier does call `askAI`) are all deterministic wherever possible, per Product Principle 2.

**AI feature files** (`src/features/ai/`), all going through the gateway: `career-mentor.ts`, `finance-advisor.ts`, `health-report.ts` (includes `askHealthCoach`, the Health bot's free-form Q&A), `coding-mentor.ts` (the Coding bot's free-form Q&A — recent streak/solved-questions/readings as context), `study-plan.ts`, `weekly-digest.ts`, `recommendations.ts` (the generic recommendations widget behind Plan Coach, Code Mentor, and half of Health Coach/Study Coach — wired into Planner, Health, Learning, and Coding only; Career and Finance have a dedicated mentor/advisor instead), `executive-summary.ts` (Planner bot's "executive summary" action — composes `generateWeeklyDigest` + one consolidated `getModuleRecommendations` call spanning every module at once, rather than a separate AI call per module; no new Gateway task, both underlying calls already route through `weekly_digest`/`module_recommendations`).

**Personal Brain** (`src/features/brain/`, Phase 2 PRD, cross-module rather than per-module): `context-builder.ts` reshapes `getDashboardData()`'s existing aggregate query into the PRD's stated context shape (no new queries beyond the two below); `calculations.ts` has `explainScore()` (deterministic, feeds Explain My Score above); `prompts.ts` + `advisor.ts` have `askBrain()` (the `brain_qa` task) and `askBrainDecision()` (the `brain_decision` task, strict-JSON structured output), feeding Ask Brain's Ask/Decide tabs above; `advisor.ts`'s `getWeeklyReflection()` is self-contained (creates its own supabase client + `auth.getUser()`, unlike the two above which take an already-built context prop) and feeds the Reflect tab; `getMonthlyReview(context)` takes the caller's `BrainContext` for its Career/Finance-total/Learning/Coding fields but is otherwise self-contained the same way, feeding the Monthly tab — see the Ask Brain entry above for what both do.

- **Pattern Detection** (`signals.ts`) — deterministic-only checks (Product Principle 2; AI is never used to compute a pattern, only to narrate one elsewhere) run weekly from the `weekly-digest` cron, four so far (Phase 3 PRD's "Weekly Pattern Mining"): workout day-of-week concentration (≥40% of last 90 days' workouts on one weekday, min. 3); a weekend protein drop (weekend avg <75% of weekday avg, needs ≥4 weekday + ≥2 weekend logged days); coding time-of-day skew (≥65% of the last 60 days' solves in one half of the day, min. 6, using `toISTHour` on `coding_daily_questions.completed_at`); and a workout→same-day-coding correlation (coding completion rate on workout days is ≥20 points higher than on rest days, min. 4 days each side). (A fifth pattern, sleep→next-day-coding correlation, was removed 2026-08-13 along with the rest of Sleep tracking — see §5.) Three more of the PRDs' example patterns (overspend-after-salary, interview-performance-vs-sleep, workout-drop-during-travel) are explicitly left out because they need data no integration currently provides (a real salary-*credit* event, interview outcomes, travel/calendar detection — Calendar/Gmail/GitHub integrations aren't planned, see `PRDs/phase3.md`'s git history for why). Matches persist to `brain_patterns` (see Database) via `upsert(onConflict: user_id,pattern)`, incrementing `times_confirmed`/`last_seen` on repeat detection so patterns genuinely accumulate rather than reset each run. `context-builder.ts`'s `weeklyPatterns` only surfaces patterns confirmed more than once (`times_confirmed > 1`) and seen in the last 30 days, so a one-off fluke isn't presented as an established pattern. `monthlyPatterns` stays an empty placeholder — no monthly-cadence pattern job exists yet.
- **Memory** — rather than a new store (Core Principle 1: the Brain never owns data), `career_profile`'s existing `current_role`/`current_company`/`target_role`/`current_salary` columns are read straight through into the context (the `career_profile` query in `getDashboardData()` was widened to select these, no new query). **Memory Evolution** (Phase 3 PRD) widened this further with Goals: `getDashboardData()` now also queries `financial_goals` (name, target/current amount, target date), threaded through as `BrainContext.finance.goals` and surfaced in Ask Brain's Ask/Decide context and Monthly Executive Review's — e.g. asking "what are my financial goals" correctly cites the real ₹ amounts and % progress, never invented ones. **Executive Memory** (Phase 4 PRD) added one more field the same way rather than inventing new speculative ones (investment philosophy, personality traits, etc. — none of the PRD's other example fields have a natural home or any feature that would actually consume them, so they were deliberately skipped): `career_profile`'s existing "Bio / Focus" free-text field (already editable on the Career page, previously never read by the Brain) is now included in `BrainContext.career.bio` and surfaced in `buildContextSummary` — e.g. asking "what's my career focus" now correctly reflects whatever the user actually wrote there.
- **Goal Engine — removed entirely (2026-08-11).** Originally a Phase 4 PRD feature: cross-module goals for Career/Learning/Coding (`src/features/goals/`, a *separate* `goals` table from `financial_goals`, which kept its own UI throughout). Its UI (`GoalsCard.tsx` and the write actions `addGoal`/`updateGoalProgress`/`toggleGoalAchieved`/`deleteGoal`) was deleted 2026-08-10, leaving only read paths (`getGoals()`, `resolveAutoMetric()`, `checkGoalProgress()`, `crossModuleGoals` threading into Ask Brain) with no way to ever create a new goal — a personal-backlog audit flagged this as "silently half-alive" (no usable feature, just dead weight in every page load that touched it), and the decision was to rip out the remaining code rather than resurrect a minimal add-goal UI. Removed: the whole `src/features/goals/` directory, `checkGoalProgress`'s Today's Focus signal, `crossModuleGoals` from `BrainContext`/`getDashboardData()`/`buildContextSummary`, and the `goalsContext` parameter (and its prompt text) from `recommendQuizTopic`/`recommendCodingQuestions`. The `goals` table itself was dropped in a 2026-08-20 schema-debt cleanup migration, along with the other deliberately-orphaned schema mentioned throughout this doc (SIP columns, `health_profile`'s `target_weight_kg`/`goal_deadline`, `coding_quiz_attempts`, `resume_versions`, `trending_readings`) — see Database below.

## 13. Astrology (`/astrology`) — added 2026-08-13, expanded 2026-08-14 (twice)

A Vedic (sidereal) horoscope module — the one module whose core output is real astronomical
calculation, never AI. Per Product Principle 2, Claude only narrates already-computed
positions; it never generates a chart itself (an AI asked to "produce a horoscope" from
scratch would hallucinate planetary positions, unacceptable for something presented as a real
chart). Origin doc: `astrology.md` at the repo root — this section is the current source of
truth for what's actually built. Built in four passes: an initial MVP (natal chart, Vimshottari
Dasha, daily reading); expanded to match a fuller Claude Design mock (Yogini Dasha,
monthly/yearly readings, Remediation); a scope increase adding Panchang, Gochara transit
analysis, the Navamsa (D9) divisional chart, a Dashboard strip, a dedicated Telegram bot + daily
cron, and a Hindi (EN/हिं) language toggle; then a further scope increase the same week adding
Chandrashtama detection, an astrology-derived daily mood forecast, a one-time Characteristics
profile, a structured daily-reading breakdown (Favorable For / Avoid / Mood Forecast /
Remediation, not just prose), and Choghadiya time-blocks. The one item `astrology.md` scoped
and then explicitly dropped mid-build (an Outcome Journal — logging how a reading's predictions
actually played out) was removed cleanly before any migration for it was applied;
compatibility/matching charts and Muhurta lookups remain explicitly out of scope.

- **Ephemeris** (`src/features/astrology/ephemeris.ts`) — `swisseph-wasm`, a WebAssembly build
  of the real Swiss Ephemeris C library. Chosen over native `swisseph` bindings specifically to
  avoid Vercel serverless native-binding deploy risk (this project has never shipped a native
  dependency); chosen over a pure-JS Meeus/VSOP87 approach (`astronomia`) for genuine
  professional-grade precision. Sidereal correction uses Swiss Ephemeris's built-in Lahiri
  ayanamsa mode (`set_sid_mode(SE_SIDM_LAHIRI, 0, 0)` + `SEFLG_SIDEREAL`), not a manual
  ayanamsa subtraction — validated at implementation time by reproducing the widely-published
  Lahiri ayanamsa value at J2000.0 (2000-01-01 12:00 UT ≈ 23.85°; this pipeline returns
  23.8571°). `next.config.ts` has two entries just for this dependency: `outputFileTracingIncludes`
  explicitly bundles `node_modules/swisseph-wasm/wasm/**` into the `/astrology` serverless
  function (the package loads its `.wasm`/`.data` files via a runtime filesystem path Vercel's
  file-tracer can't discover through static analysis alone), and `serverExternalPackages:
  ['swisseph-wasm']` keeps the package out of webpack's bundling entirely (webpack was breaking
  the package's `await import('node:module')` call for `createRequire`, throwing
  "createRequire is not a function" — reproduced locally, fixed by this config, both real bugs
  caught during implementation, not anticipated by the original doc).
- **Chart calculation** (`src/features/astrology/chart-calculations.ts`, pure functions, no AI,
  same pattern as Health's `calculations.ts`) — rashi (sign) + nakshatra + pada from sidereal
  longitude, whole-sign house placement from the Lagna, and two dasha timelines, both computed
  once at profile save via `upsertAstrologyProfile()` and stored in `natal_chart` jsonb (never
  recomputed on read, so they can't silently drift):
  - **Vimshottari Dasha** — the primary/default system, a 120-year cycle across the 9 classical
    grahas (Sun/Moon/Mars/Mercury/Jupiter/Venus/Saturn/Rahu/Ketu, not the outer planets Western
    astrology adds), keyed off the Moon's birth nakshatra, both Mahadasha and nested Antardasha
    periods.
  - **Yogini Dasha** — a secondary, shorter 36-year cycle across 8 Yoginis, also keyed off the
    Moon's birth nakshatra but with its own lord order/year-lengths and starting-point formula
    (`(nakshatraNumber + 3) mod 8`, the classical Devi Bhagavata formula). Single-level only, no
    antardasha subdivision. Verified 2026-08-18 against the full published 27-nakshatra →
    starting-Yogini table (cross-checked via three independent sources) — this surfaced a real
    bug: the formula previously had an erroneous extra `× 2` (`(nakshatraNumber × 2 + 3) mod 8`),
    which produced the wrong starting lord for every chart. Fixed as part of this verification.
- **Natal chart display** — a North Indian style kundli (`KundliChart.tsx`, SVG): fixed house
  positions (house 1 always the top-center diamond, numbered counter-clockwise), planets
  placed by house with standard 2-letter abbreviations, rashi number shown per house. The
  design mock's own natal-chart card used a simplified 3×12 grid with a footnote explicitly
  saying "production renders a true North Indian diamond kundli" — this SVG is that production
  version, so it was kept as-is rather than downgraded to match the grid literally.
- **Current Dasha strip** — accent-tinted banner showing the active Vimshottari
  Mahadasha/Antardasha + until-date (`getCurrentDasha()`, looked up against today's date, not
  recomputed) with the active Yogini period as a secondary line, right-aligned
  (`getCurrentYogini()`).
- **Horoscope** — a Today/This Month/This Year tab switcher. All three periods read the same
  current-transit snapshot (this module doesn't compute a forward window of planetary movement)
  — only the prompt's framing changes, the same way a monthly financial digest still runs off
  today's numbers rather than projecting the month. The AI prompt contains only computed
  positions/dasha state, never raw birth data. **Daily is structured, not prose**: a one-line summary
  (prompt tightened 2026-09-24 for crisp output: summary ONE sentence ≤20 words, 2–3 favorable and
  1–2 avoid phrases of 3–8 words with no explanations, mood ONE sentence ≤15 words; monthly/yearly
  prose = exactly 4 sentences ≤15 words each, <70 words; characteristics = exactly 5 sentences ≤16
  words each, <90 words — shared by web and Telegram, each prompt change regenerated once), then — matching the Claude Design source's exact layout (pulled and matched
  2026-08-14) — a side-by-side 2-column grid (green Favorable-For card / red Avoid card, each a
  bulleted list, not chip pills) and a Mood Forecast card below it with a conditional ⚠
  Chandrashtama warning line rendered off the deterministic `isChandrashtama` flag (decoupled
  from whatever the model's own mood prose says — the warning is UI-driven, not text-matched).
  From `getStructuredDailyReading(profile, lang)` — the model returns strict JSON
  (`{summary, favorableFor, avoid, moodForecast}`, parsed with the same regex-extract +
  try/catch + graceful-fallback pattern `brain_decision` already uses elsewhere); `remediation`
  is filled in afterward from the same curated `getRemediation()` table the standalone
  Remediation card uses (kept on the `DailyReading` type for the Telegram bot's flattened prose,
  but the design mock doesn't repeat it inside this card — the standalone Remediation card below
  is the only place it renders on the web page, avoiding the duplication an earlier draft had).
  **Monthly/yearly stay prose** (`getAstrologyReading(profile, period, lang)`) — "avoid X today"
  and a Moon-transit mood forecast don't translate to a month/year scale the same way. Both
  functions share one `buildReadingContext()` helper for the ephemeris/gochara/dasha work so
  they can't drift out of sync with each other, and both go through the same `astrology_reading`
  AI task (§12) — calling `getAstrologyReading(profile, 'daily', lang)` (e.g. from the Telegram
  bot or the daily cron) internally calls the same `getStructuredDailyReading` and flattens its
  JSON into readable prose, so a web-page view and a same-day Telegram request hit the identical
  cache entry rather than double-spending.
- **Remediation** — up to 3 traditional remedies for the chart's Saturn/Rahu/Ketu/Mars/Moon
  placements, sourced from a curated per-planet template table
  (`src/features/astrology/remedies.ts`) parameterized with each planet's actual house number.
  Deliberately **not** an AI Gateway call at all — narration is template text substitution, not
  free-form generation, per `astrology.md`'s explicit anti-hallucination requirement for this
  feature ("not left to the model to invent").
- **Birth Details card** — compact inline-editable field grid matching Career Profile's density
  (not a standalone form card), since birth details are effectively write-once. Unlike Career's
  per-field independent saves, every field here saves together in one submit — the natal chart
  is a function of all of them at once, so editing just one in isolation would leave the stored
  chart inconsistent with the rest.
- **Panchang** (`src/features/astrology/panchang.ts` + `panchang-actions.ts`) — the daily Hindu
  calendar: tithi (+ paksha), nakshatra-of-the-day (distinct from natal nakshatra), yoga,
  karana, sunrise/sunset, and the three inauspicious windows (Rahu Kalam, Yamaganda, Gulika
  Kalam — fixed per-weekday segment lookup tables over the sunrise–sunset span). Global, not
  birth-dependent, computed from Sun/Moon sidereal longitudes at sunrise (not local midnight —
  matches how printed panchangs work) via `getTodaysPanchang(lat, lng, utcOffsetHours)`, which
  checks `panchang_daily` for today's row first and only computes+upserts if missing — reused
  everywhere "today's panchang" is needed rather than recomputed per request. Location-dependent
  (sunrise/sunset/kalam windows shift by place); defaults to the profile's birth-place
  coordinates, the only location this app currently tracks. All the underlying sunrise/sunset
  and "HH:MM local" ephemeris helpers are timezone-aware by construction (`julianDayLocalMidnightUt`,
  `jdToLocalHHMM`) — an earlier draft computed these in raw UT, which would have shown the wrong
  local day/hour for a sunrise near UTC midnight; caught and fixed before shipping.
- **Gochara** (transit analysis, `src/features/astrology/gochara.ts`) — for each planet's
  current sidereal position, computes house-from-Lagna and house-from-Moon relative to the
  natal chart (both are standard reference points; a first pass surfaces all current transits
  rather than scoring their significance, which `astrology.md` explicitly defers).
  Deterministic, no new ephemeris calls beyond the existing transit snapshot. Backend-only:
  feeds into the `astrology_reading` prompt context (dasha + gochara together, the standard
  "which life theme is active + how today's sky affects it" combination) and into
  `isChandrashtama()` below, but is **not rendered as its own UI element** — the persistent
  per-planet transit list that used to sit inside the Horoscope card was removed to match the
  current Claude Design source (pulled and matched 2026-08-15, which no longer shows it), and
  the now-unused `getCurrentGochara(profile)` wrapper action was deleted along with it (unlike
  Panchang below, `computeGochara`/`isChandrashtama` in `gochara.ts` itself still has real
  callers, so only the dedicated page-facing wrapper was removed, not the engine).
  `isChandrashtama()` is one dedicated flag on top of the same computed data: true when the
  transiting Moon's own gochara entry has `houseFromMoon === 8` — a lookup against data already
  computed, not a new formula, so it doesn't carry its own separate verification caveat the way
  Yogini Dasha's starting-lord formula does. Chandrashtama is a well-defined traditional
  rule-of-thumb marking an emotionally lower/more cautious day — the concrete astronomical basis
  the mood forecast below is grounded in, not an AI guess.
- **Navamsa (D9)** — a second chart derived mathematically from the D1 (Rashi) positions via a
  fixed divisional formula (`(rashiIndex × 9 + navamsaNumber − 1) mod 12`, `computeNavamsa()` in
  `chart-calculations.ts`), not a new ephemeris call. Computed once at profile save alongside
  the two dasha timelines and stored in the same `natal_chart` jsonb (`NavamsaChart { lagna,
  planets }`). The Natal Chart card has a Rashi (D1) / Navamsa (D9) tab toggle over the same
  `KundliChart` SVG renderer (widened to accept either chart's minimal `{ planet, house,
  retrograde? }` shape, so it doesn't care which divisional chart it's drawing). Feeds into the
  `astrology_reading` prompt context the same way Gochara does.
- **Your Characteristics card** — a one-time narrative (Lagna qualities, Moon sign/mind nature,
  notable strong/weak placements, general tendencies), grounded only in the natal chart +
  Navamsa, distinct from the daily/monthly/yearly readings in that it's not a forecast — a
  stable read that only needs to change when birth details are re-edited. Collapsed by default
  behind a native `<details>`/`<summary>` accordion (2026-08-18, same pattern Planner's
  Completed-tasks list already uses) — the card's title doubles as the toggle, rather than a
  separate `Card` title + always-expanded body.
  `getAstrologyCharacteristics(profile, lang)` uses its own AI Gateway task
  (`astrology_characteristics`, Sonnet) with an effectively-permanent cache (`ONE_YEAR` TTL in
  `TASK_CONFIG` — a ceiling, not the thing doing the real work: the cache key already changes
  whenever the chart itself changes, since the chart data is what's in the prompt). Auto-loads
  on page view (unlike the click-to-load daily/monthly/yearly tabs) since a repeat view costs
  nothing once cached. Uses `askAIWithMeta()` (§12) and shows an "Updated {relative time}" line
  below the narrative (added 2026-08-20) — with a year-long cache TTL this is the card where a
  freshness hint matters most, since the text can otherwise look current for a very long time
  after the chart last actually changed.
- **Panchang engine (backend only, no page card since 2026-08-14)** — the "Today's Panchang"
  card and its Choghadiya section were removed from the Astrology page's UI per direct request
  (`PanchangCard`, `CHOGHADIYA_COLOR`, the `panchang` state/effect, and the now-unused Hindi
  dictionary entries for panchang/choghadiya vocabulary were all deleted from
  `AstrologyView.tsx`/`i18n/hi.ts` in the same cleanup). The underlying engine
  (`panchang.ts`/`panchang-actions.ts`, `panchang_daily` table incl. `choghadiya` jsonb) is
  **not** removed — it still powers the Dashboard strip's tithi/nakshatra (below), the Telegram
  bot's "today's panchang" command, the `astrology-daily` cron's push, and the daily reading's
  mood-forecast tithi context (§13's AI Gateway note) — all real consumers outside the page's
  own UI, out of scope for this removal. `getChoghadiya()` still computes the full traditional
  16 blocks (8 day, sunrise-sunset, + 8 night, sunset-*next*-sunrise) reconstructed from
  commonly-published panchang references — verified 2026-08-18 against Drik Panchang's
  published Choghadiya table for a real date/location; all 16 blocks (names, order, and
  weekday-start indices for both the day and night cycles) matched exactly. Unlike the rest of
  `panchang_daily`'s columns, Choghadiya itself had zero consumers even outside the page (the
  removed card was genuinely its only reader) until 2026-08-18, when a new
  `getCurrentChoghadiyaBlock()` helper (picks the single currently-active block out of the 16,
  handling the night blocks that run past midnight) was wired into both the Telegram bot's
  "today's panchang" reply and the `astrology-daily` cron's morning push — a formatting change
  only, no new computation, since the data was already being computed and stored either way.
- **Dashboard integration** — a compact "🔮 Astrology · [Mahadasha]/[Antardasha] dasha ·
  [tithi] · [nakshatra]" strip, positioned right after the Top Priority banner (matching the
  Claude Design source exactly, pulled and matched 2026-08-14 — an earlier draft placed it near
  the bottom of the page with extra fields; moved up and trimmed to match). Deliberately minimal
  — no until-date, no Yogini, that detail lives on the Astrology page itself.
  `getDashboardData()` adds two cheap reads — `astrology_profile.natal_chart` and today's
  `panchang_daily` row — and reuses the same `getCurrentDasha` pure function the Astrology page
  itself calls; no ephemeris recompute, no new AI call. Only rendered once a birth chart exists.

## 14. Prep (`/prep`) — v2.0, added 2026-09-24

The center of v2 (`ROADMAP-v2.md`): one place that answers *"what do I practice today, and am I getting interview-ready?"* for a Frontend Tech Lead / Senior UI role. Added after a usage audit found ~9 separate daily items (4–5 coding picks, a daily read, workout, metrics, expenses) and a September collapse in practice (coding 15/92, reads 1/20), with no behavioral, leadership, or system-design practice anywhere. Code in `src/features/prep/`; three tabs (`PageTabs`), deep-linkable via `?tab=today|flashcards|stories`.

- **Today's Prep** (`plan.ts`, deterministic) — one sequenced ~50-min session per day, persisted in `prep_sessions` (one row per user+date, `blocks` jsonb) so the plan doesn't shift mid-day. Four blocks: **Flashcards** warm-up (5 min, 15 on Sunday) → **main practice** (25–40 min, by weekday focus) → **Concept** (10 min: the active daily read (§6) if unread, else a quiz on the weakest area) → **Leadership rep** (5 min: draft a story for the first uncovered competency, or rehearse one). Weekday focus: Sun Review & reset · Mon JavaScript & TypeScript depth (the active JS-function pick) · Tue React & Next.js internals · Wed Frontend system design · Thu UI coding (the active UI-coding pick) · Fri Behavioral & leadership · Sat Mock round (timed quiz on the weakest area + the active algorithm pick). Each block is ticked manually (`togglePrepBlock()`); the warm-up auto-ticks once nothing is due or 10 cards were reviewed today. A session is complete when all 4 blocks are done (`completed_at`); the prep streak counts consecutive completed days (today given grace).
- **Interview Readiness matrix** (`readiness.ts`, deterministic) — 12 areas (`READINESS_AREAS` in `prep/types.ts`): JavaScript depth, TypeScript, React/Next.js, CSS & layout, Accessibility, Performance, Testing, Browser/network/security, Frontend system design, UI coding, Behavioral, Leadership. Each area averages whatever real signal exists: the recency-weighted Career topic-quiz readiness (`computeReadiness`) of its mapped quiz topics, and self-reported outcomes (solved 100 / with help 60 / struggled 30 / no outcome 70) of coding questions completed in the last 90 days on its mapped topics or category (≥2 needed). Behavioral/Leadership use Story Bank coverage (a competency counts when it has a story rated ≥3/5, weaker ones count half). `null` = no data ("blind spot"). Overall readiness = mean with blind spots as 0; "Next focus" = the 3 lowest (blind spots first).
- **Flashcards** (`srs.ts`) — every wrong answer in a Career topic quiz or a Learning resource quiz becomes a card automatically (question → correct option + stored explanation), synced idempotently on each Prep load via `flashcards.source_ref` (`<source>:<attempt id>:<question index>`, unique per user); manual cards too. SM-2-style deterministic scheduling: Again → 1 day, ease −0.2, lapse+1; Hard → slow growth, ease −0.15; Good → 1d, 6d, then × ease; Easy → faster, ease +0.15; ease floored at 1.3. Each grade button previews its next interval. "Review ahead" when nothing is due.
- **Story Bank** — STAR stories (`stories`: title, competencies[], situation/task/action/result, metrics, strength 1–5) tagged across 10 competencies (`COMPETENCIES`: Leadership — ownership, mentoring, influence, technical decision, raising the bar; Behavioral — conflict, ambiguity, failure, delivery under pressure, cross-team collaboration), shown as a coverage grid (✓ covered / ◐ draft / ○ none). **Rehearse** shows a static "Tell me about a time…" prompt for the chosen competency (`REHEARSAL_PROMPTS`, shuffleable), optionally linked to a story; the typed answer gets an AI critique (`rehearseStory()` → `askAI('story_critique', ...)`, Sonnet, uncached — the only AI in the module; fixed shape: Verdict / What worked / Fix next / Likely follow-up, under 180 words), saved to `story_rehearsals`.

## Architecture

**Thin page + feature view pattern:**

- `src/app/[route]/page.tsx` — async server component, fetches data, passes to view
- `src/features/[module]/components/[Module]View.tsx` — `'use client'` component, owns all interactivity
- `src/features/[module]/actions.ts` — `'use server'` functions (CRUD via Supabase)
- `src/features/[module]/types.ts` — TypeScript types for the module

**Optimistic UI:** mutations use `useOptimistic` + `useTransition` so the UI updates instantly before the server confirms.

**Supabase clients:**

- `src/lib/supabase/server.ts` — server components and server actions (cookies-based, RLS-scoped to the logged-in user)
- `src/lib/supabase/client.ts` — client components (browser)
- `src/lib/supabase/service.ts` — service-role client (used by cron jobs and the Telegram webhook — bypasses RLS since those code paths run without a browser session)
- `src/lib/supabase/middleware.ts` — session refresh + redirect logic, wired in root `src/middleware.ts` (matcher excludes `/api`, `_next/static`, `_next/image`, favicon, and image assets — so Telegram/cron webhooks are never gated by the browser auth check). Unauthenticated users on a page route are redirected to `/login`; authenticated users hitting `/login` are redirected to `/planner` (the authenticated landing page — distinct from `/dashboard`).

**Loading / error states:**

- `src/app/[route]/loading.tsx` — skeleton shown while the server fetches data
- `src/app/[route]/error.tsx` — error boundary with a "Try again" reset button

**Shared components** (`src/components/`): `TopNav` (header + desktop nav + mobile bottom bar, combined), `ProfileMenu`, `Card` (`h-full flex flex-col` by default, added 2026-08-22 — stretches to fill its grid cell when siblings are taller, e.g. Coding's 4-card daily-pick row, letting each card's own bottom content, like an action-button row, line up with `mt-auto` instead of trailing at whatever height that card's own content happened to produce), `Modal` (generic modal shell — title/close/footer chrome + shared field style constants, used by all 10 data-entry modals across Career/Finance/Health/Coding/Learning/Settings), `ConfirmDialog` (built on `Modal` — title/description + Cancel/destructive-styled confirm button, gates every hard-delete action in the UI: Planner task, Career application, Finance loan/investment/goal/expense, Health workout, Learning resource, Settings reminder — each call site supplies its own item-specific description text), `EmptyState`, `Skeleton`, `AIAdvisorProvider`, `PageTabs` (added 2026-08-20 — a generic underline-style tab bar, `{key, label}[]` + active key + onChange, horizontally scrollable so it never breaks layout on narrow viewports; used by Career and Finance to split their 4+ sub-sections into tabs per the density rule below rather than one long vertical scroll).

**AI advisor header architecture** — every module's whole-page AI advisor (Plan Coach, Career Mentor, Money Advisor, Health Coach, Study Coach, Code Mentor) lives in the top nav bar, not inline in page content. `TopNav.tsx` is a separate component from each page's `*View.tsx` in the layout tree and can't read a page's local state directly, so `AIAdvisorProvider` (wrapping the whole app in root `layout.tsx`) provides a shared registration slot: each View calls `useAIAdvisor(label, icon, content)` once, which registers the trigger's label/icon and portals `content` (real JSX from that View's own render, with full access to its local state) directly into the panel body DOM node via `createPortal` — content never round-trips through Context state, so typing/interacting inside the panel only re-renders the View itself, not the Provider (an earlier version that lifted content into Context state caused an infinite re-render loop; portaling was the fix). `TopNav.tsx` reads the currently-registered trigger via `useAIAdvisorTrigger()` and renders nothing on routes with no registered advisor (Settings). Not every AI feature moved here — only whole-page advisors did; per-item contextual AI (Career's bulk "AI Generate" interview questions, Learning's per-resource "Quiz me") stays inline, tied to whichever item is selected. Planner's **Executive Summary** trigger is a deliberate exception to this shared-slot pattern — see §2 below. Every advisor open (`AIAdvisorProvider`'s shared `toggle`) and every tab switch within a multi-tab advisor (Money Advisor, Health Coach, Study Coach, Ask Brain — each own their own local tab state, so each logs from its own tab-click handler) fires `logAdvisorUsage()` into `advisor_usage_log` (see Database) — Executive Summary logs from its own separate trigger too, despite bypassing the shared provider otherwise.

**Navigation structure** — a single `TopNav` component (not a desktop `Sidebar` + separate mobile `BottomNav` — an earlier PRD-v2 design called for pillar-grouped Learn/Build/Perform/Recover navigation in a collapsible sidebar, but the shipped nav is flat, ungrouped, and the same component handles both viewports). Desktop (`md:` and up) shows a flat row of 8 text-only nav pills (Dashboard, **Prep** (v2.0), Planner, Career, Finance, Health, Learning, Coding — Settings and Astrology both live in `ProfileMenu` instead, not top-level nav). Below `md:`, the same component instead renders a fixed bottom bar with 4 primary tabs (Home, Prep, Health, Finance — Prep replaced Planner 2026-09-24, Planner moved into More) plus a "More" sheet for everything else (Planner, Career, Learning, Coding, Astrology, Settings — Astrology appears in both the mobile "More" sheet and the profile dropdown, same redundancy Settings already had). See "Navigation — TopNav" below for full detail.

## Database

Standard pattern: `user_id uuid references auth.users` + 4 RLS policies (select/insert/update/delete scoped to `auth.uid()`), except where noted.

**Schema-debt cleanup (2026-08-20):** this app previously had a policy of leaving orphaned tables/columns in place rather than migrating them away once a feature was removed — each individual call made sense at the time, but it accumulated into real cognitive load (every future reader had to re-learn which columns were dead). A single pass (`20260820b_schema_debt_cleanup.sql`, `20260820c_drop_interview_qa.sql`) dropped everything confirmed to have zero remaining code readers: the `goals`, `coding_quiz_attempts`, `resume_versions`, `trending_readings`, and `interview_qa` tables outright, plus `investments`' 4 SIP columns, `health_metrics.sleep_hours`/`water_ml`, and `health_profile.target_weight_kg`/`goal_deadline`. Two of these (`trending_readings`, `health_profile`'s two columns) still had live — if functionally pointless — reads/writes in `planner/actions.ts`, `telegram/handler.ts`, `health/actions.ts`, `health/types.ts`, and `HealthProfileForm.tsx`; those references were removed in the same change, before the drop. Going forward, the standing rule is: when a feature is fully removed, drop its schema in the same change rather than leaving it "for backward compatibility" — nothing in this single-user app's history has ever actually needed an orphaned column back.

This app is a single-user system — there's no way around some manual setup and a specific order of operations, since a few values (your own user ID, your own Telegram chat ID) don't exist until you've deployed once and signed up. Steps:

1. **Create a Supabase project** at [supabase.com](https://supabase.com) (free tier is enough). Get `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` from Project Settings → API.
2. **Run every file in `supabase/migrations/`** against that project, in filename order (Supabase Dashboard → SQL Editor, or the Supabase CLI).
3. **Get an Anthropic API key** at [console.anthropic.com](https://console.anthropic.com) (`ANTHROPIC_API_KEY`). Optionally get a Groq key at [console.groq.com](https://console.groq.com) (`GROQ_API_KEY`) — only needed for Telegram voice-note transcription; the app works without it.
4. **Generate `CRON_SECRET`** — any random string (e.g. `openssl rand -hex 32`).
5. **Deploy** — click the button above, or `vercel deploy`, setting the env vars from steps 1–4.
6. **Create your account, then lock signups down immediately — in that order, don't leave a gap.** The app has no invite gate of its own: by default the `/login` page's "Sign up" button lets anyone create an account against your database, and that window is open the moment your deployment is reachable. Two ways to close it:
   - **Safer — skip public signup entirely:** create your own (already-confirmed) user via Supabase Dashboard → Authentication → Users → "Add user", then log in directly at `/login` with that email/password. Public signup never needs to be enabled at all.
   - **Faster, if you're doing this in one sitting:** sign up normally at `https://<your-deployment>/login`, confirm your email, log in — then immediately go lock it down (next bullet) before doing anything else. Don't leave the tab open and come back to it later.
   Either way, then **lock down signups** in Supabase (Authentication → Sign In / Providers) — turn off the sign-up-enabled setting so `/login`'s "Sign up" button can no longer create new accounts.
7. Copy your user's UUID from Supabase Dashboard → Authentication → Users, and add it to your Vercel project's environment variables as `SUPABASE_USER_ID`, then redeploy — cron jobs and the Telegram bots use this to know whose data to act on.
8. *(Optional, for Telegram)* Create one bot per module you want via [@BotFather](https://t.me/BotFather), set the resulting `TELEGRAM_BOT_TOKEN_*` env vars, message any of your new bots once to learn your chat ID (e.g. via [@userinfobot](https://t.me/userinfobot)) and set `TELEGRAM_ALLOWED_CHAT_ID`, redeploy, then run:

   ```bash
   node scripts/setup-webhooks.mjs https://your-app.vercel.app
   ```

### Security model

This app assumes **exactly one user account per deployment.** Most tables enforce that with owner-scoped RLS (`auth.uid() = user_id`, the standard pattern this doc calls out at the top of the Database section) — but a handful of tables have no per-user concept at all, either because they're genuinely global/shared pools or system-level logs, and their RLS policies are scoped to *any authenticated user of this deployment*, not to a specific owner:

- `telegram_logs`, `panchang_daily`, `cron_runs` — system/cross-cutting logs with no natural single owner
- `workout_library`, `coding_questions`, `coding_tips`, `health_tips`, `learning_tips` — global curated content pools, no `user_id` column at all

For a true single-user deployment (the only configuration this app is built and tested for) this is correct and intentional — there's only ever one authenticated user, so "any authenticated user" and "the owner" are the same person. **If you fork this and ever add a second account to your deployment, audit these tables first** — a second account would be able to read all of them (though never any other user's owner-scoped data, like `tasks` or `expenses`, which stay properly isolated per-user regardless). This isn't a bug to fix; it's a deliberate simplification that only holds under the single-user assumption stated above.

## Design System

**Theme**: both dark and light are live, `[data-theme="dark"|"light"]` on `<html>` (`src/app/layout.tsx`), not a hardcoded `.dark` class. The version string (`v{package.json's version}`) is a link to **`/changelog`** (added 2026-08-20) — a plain server component that reads `CHANGELOG.md` from the repo root and renders its `## {date}` / `- {item}` structure (a hand-rolled two-line parser, same "don't pull in a markdown library for two syntax patterns" choice as `FormattedText.tsx`'s bold/italic renderer). Deterministic, no AI, no database table — the changelog is the file itself, appended to by hand alongside each version bump; not auto-generated from commit messages. Settings isn't in this list; it lives in `ProfileMenu` instead. Active pill: `bg-surface-2 text-fg-primary`; inactive: `text-fg-tertiary`. Right side, all viewports: theme toggle, the currently-registered AI-advisor trigger button (icon + label + a chevron that rotates when open — rendered only on routes with one registered, e.g. absent on Settings), and `ProfileMenu` (avatar/email/sign-out — the current equivalent of what used to be a separate `UserInfo` component). No budget/spend indicator lives in the header (that lives on Settings' AI Budget card and Dashboard's Bot Activity card header instead).

Below `md:`, the same `TopNav` component additionally renders a fixed bottom bar: 4 primary tabs — **Home, Prep, Health, Finance** (Prep replaced Planner 2026-09-24) — plus a **More** button opening a bottom sheet (slide-up panel, backdrop-dismiss) listing **Planner, Career, Learning, Coding, Astrology, Settings**. Active color `text-accent`, inactive `text-fg-tertiary`.

**AI Advisor panel** (the shared slide-down/portal panel every module's whole-page AI feature uses — Plan Coach, Career Mentor, Money Advisor, Health Coach, Study Coach, Code Mentor, Ask Brain): triggered from `TopNav`'s advisor button, renders as a fixed panel `top-14 right-4/6`, `380px` wide, `max-h-[75vh]` scrollable, `bg-surface-1` with a `shadow-2xl` and a slide-in-from-top + fade entrance, dismissed by backdrop click, its own `X` button, or navigating away. Internally, multi-tab advisors (Money Advisor: Ask/Simulate; Health Coach: Recommendations/Weekly Report; Study Coach: Recommendations/Daily Plan; Ask Brain: Ask/Decide/Reflect/Monthly) use an identical pill-toggle tab bar (`bg-surface-2` track, active tab `bg-accent text-white`).

**Modal shell** (used identically everywhere a modal appears — Add Application, Add Loan/Investment/Goal/Expense, Health Profile, Coding Settings, Outcome picker, New Reminder, quizzes): full-screen `bg-black/60` backdrop, centered panel `bg-surface-1 border border-surface-3 rounded-xl p-6` (`max-w-sm` for simple forms, `max-w-md`/`max-w-lg` for richer ones like quizzes), fade+zoom-in entrance, header row = title + `X` close, dismissible via Escape key or backdrop click.

**Shared primitives**:

- **Card** (`bg-surface-1 border border-surface-3 rounded-xl`, default `p-4` padding, usually overridden to `p-3.5`) — the base wrapper for nearly every widget on every page. Optional uppercase title row with a right-aligned `action` slot (a button, icon, or filter toggle).
- **EmptyState** — centered icon (slate-700) + message (slate-600) + optional accent CTA button with a `Plus` icon; a `compact` variant reduces vertical padding for use inside an already-titled Card.
- **StatCard** — centered big number (`text-2xl font-bold`) over a small label, used for all summary-stat rows (Planner's Pending/High Priority/Overdue/Completed, Learning's Total/In Progress/Completed/Streak, etc).
- **FilterPill** — a toggle-button pill, inactive = `bg-surface-1 border-surface-3 text-slate-400`, active = `bg-accent text-white` (or a status-tinted color when used for status filters, e.g. Learning's Not Started/Completed pills).
- **InlineEdit** pattern (Finance) — a value renders as a plain button with a hover-revealed pencil icon; clicking swaps it for a focused text input + a green checkmark save button, Enter saves, Escape cancels. Used for salary, loan EMI/rate/months, investment amounts. Health's metric tiles use a simpler always-editable variant (bare `<input>` embedded in the tile, saves on blur/Enter, flashes a green checkmark on success) rather than a click-to-reveal step.
- **Skeleton loading states** — no spinners anywhere in the app; every loading state is `animate-pulse` gray bars (`bg-surface-2`) at varying widths, either a generic `CardSkeleton`/`ListSkeleton`/`StatsSkeleton` (route-level `loading.tsx` files) or a component-local 3–6-bar stack (AI panel responses, chart lazy-load placeholders).
- **Route-level error state** (`error.tsx`, identical on every page): centered `AlertCircle` icon (red, 60% opacity) + "Something went wrong" heading + a "Try again" button.

**Charts**: every chart in the app is `recharts`, always lazy-loaded via `next/dynamic({ ssr: false })` behind a pulsing placeholder block (never blocks initial page paint) — Dashboard's Life Score Trend, Health's Health Trend, Finance's Spending History (a bar chart + a category pie/legend). (Coding's Difficulty Progression chart was removed 2026-08-10, §7.) All colors/fonts/spacing are read from one shared config module, `src/lib/chart-theme.ts` (grid stroke, axis tick style, tooltip box class, and a 5-color chart palette on `--chart-1..5`), rather than repeated per component — built during a 2026-08-10 chart-fidelity pass against the design's actual chart markup (`audit/CHARTS-AUDIT.md` has the full per-property audit). Key specifics per chart, since the design turned out to specify real per-chart behavior rather than one shared recipe:

- **Life Score Trend** — an `AreaChart` (line + `var(--accent-soft)` fill, not a bare line), `type="linear"` (straight segments, not smoothed), a **dynamic Y domain** (the series' own min/max with a small padding margin, not a fixed 0–100 scale, so a narrow score range still fills the chart height instead of flattening near the middle), 3 fixed `ReferenceLine`s at the domain's min/mid/max standing in for gridlines, and **persistent point dots in Weekly view only** (Monthly shows none) — matching the design's own `isTrendWeekly`-gated dot rendering exactly, not a hover-only `activeDot`.
- **Spending History bar chart** — no gridlines, no axis line, an explicit `domain={[0, 'dataMax']}` (bars scale to the exact 12-month max, no recharts "nice number" headroom), all 12 month labels shown (not every-other).
- **Spending History pie** — a **solid pie, no donut hole** (`innerRadius={0}`) and `paddingAngle={0}` (segments are contiguous, no gaps) — matches the design's literal `conic-gradient` circle. Category colors are a fixed 5-name lookup (`Housing`/`Bills`/`Transport`/`Food`/`Entertainment` → `--chart-1..5`, the design's own mapping) with every other category falling back to `var(--border-strong)`, not the old per-category rainbow of hardcoded hex.
- **Health Trend** has no design counterpart at all (the design's Health screen has zero chart markup) — kept as real functionality beyond the mock, `type="monotone"` unchanged, just repainted to read its grid/axis/tooltip colors and its 4 metric-series colors from the shared theme module instead of hardcoded hex that silently broke in light theme.
- Tooltips are real interactivity kept on every chart despite the static design mock showing no hover state at all for any of them (same "real functionality beyond a static mock" precedent used throughout this project's other audits).

The two ring/gauge visualizations (Dashboard's big Life Score ring, Health's Health Score ring, and every small `MiniRing`) are hand-drawn SVG with a purple→cyan or green→cyan gradient stroke, not recharts.

**Iconography**: `lucide-react` throughout, no other icon set — with one deliberate exception: Astrology uses the 🔮 emoji everywhere it's referenced (Dashboard strip, Bot Activity rows, Telegram replies) rather than a `lucide-react` icon, since a crystal-ball glyph reads more immediately as "astrology" than any available line icon and the emoji was already established across the module before this doc was audited; not a gap to silently fix by swapping it for a lucide icon. Sizes are almost always 11–16px inline with text, 18–32px for empty-state/placeholder icons. Module-to-icon mapping is consistent everywhere a module is referenced (nav, Bot Activity rows, reminders): Planner `CalendarDays`, Career `Briefcase`, Finance `DollarSign`, Health `HeartPulse`, Learning `BookOpen`, Coding `Code2`, Dashboard `LayoutDashboard`, Settings `Settings`, Astrology 🔮 (emoji, see above).

**Currency/number formatting**: ₹ amounts use `Intl.NumberFormat('en-IN', { style: 'currency', currency: 'INR', maximumFractionDigits: 0 })` (Indian digit grouping, e.g. `₹1,20,000`, no decimals) everywhere in Finance/Dashboard. AI spend (`$`) formats to 4 decimals when under a cent, else 2. Numbers that update live (scores, counters) use `tabular-nums` so digits don't jitter horizontally as they change.
