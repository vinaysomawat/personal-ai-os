A personal, single-user AI Operating System: one Next.js app that tracks interview prep, career, money, health, coding practice, and a personal knowledge base — with Claude generating insight in every module, a per-module Telegram bot for hands-free logging (text, voice, or photo), scheduled proactive nudges, and a gamified "Life Score" that rolls all of it into one daily number.

This document describes exactly what the app does today, module by module, field by field, formula by formula, so it can be pasted into a fresh AI chat and give that AI complete understanding of the system with no other context needed. It is kept current with every functional change (see `CLAUDE.md`'s post-task checklist).

**Status:** this is a personal project built for one person's specific life and workflow — not a product, and not designed for multi-tenant use. It's open-sourced as a working example of an AI-assisted personal system (Next.js + Supabase + Claude + Telegram), not as a tool meant to be deployed as-is for someone else's life. Fork it, borrow the patterns you like, adapt the modules you don't need.

To run your own instance: clone the repo, `npm install`, copy `.env.example` to `.env.local` and fill in your own Supabase project / Anthropic key / Telegram bot tokens (see [Environment variables](#environment-variables)), run the SQL files in `supabase/migrations/` against your Supabase project in order, then `npm run dev`. ## 1. Dashboard (`/dashboard`)

The home screen. Server-computed on every load (`src/features/dashboard/actions.ts`):

- **Life Score (0–100)** (v2, 2026-08-23) — every module score is a blend of two numbers, not one, so it actually responds to what you log instead of just what you touched:
  `moduleScore_M = dailyRaw_M × 0.6 + weeklyAvg_M × 0.4` (weights in `LIFE_SCORE_THRESHOLDS.dailyWeight`/`.weeklyWeight`, `src/lib/thresholds.ts`), then
  `lifeScore = round(Σ moduleScore_M × categoryWeight_M)` with the category weights `health×0.30 + finance×0.25 + career×0.25 + projects×0.20` (reweighted 2026-10-08 when Learning was removed; was `health×0.25 + finance×0.20 + career×0.20 + learning×0.20 + projects×0.15`).
  - **Why a blend, not a pure daily snapshot or a pure weekly average**: a pure daily score (v1) meant a module could sit at a misleadingly high number forever just because something was *logged* that day, regardless of whether the logged value was actually good — the exact bug that prompted this rewrite (eating well over a fat-loss calorie target didn't move the score, because v1's Health score only checked presence, not accuracy). A pure weekly average would remove all same-day feedback — nothing you do today would move the ring until tomorrow. The 60/40 blend keeps today's real effort visibly moving the number the same day, while the 40% weekly component stops one lucky day from fully erasing a bad week or one bad day from tanking a genuinely strong one.
  - **`dailyRaw_M`** — today's fresh, quality-aware snapshot, judged against a real target where one exists (see the 5 formulas below). This is the only figure ever persisted to `life_score_logs` per module — **never the blended figure**, since storing a blend would make tomorrow's weekly average partly an average of an average, compounding every day into an effectively unmovable number. `lifeScore` itself is the one exception: it's stored already-blended, since nothing ever averages `life_score` back into a future computation (only the 5 per-module raw scores feed the weekly averages).
  - **`weeklyAvg_M`** — the mean of that same raw score over the trailing 7 days including today, computed at read time from `scoreHistory` (already fetched, no new query). A day in that window with no `life_score_logs` row at all (app wasn't opened, so nothing was ever computed) counts as **0**, not excluded from the average — otherwise skipping the app on a bad day would let someone game the weekly number. Exception: an account less than 7 days old averages only over the days that exist since signup (`user.created_at`), so a brand-new account's first week isn't crushed toward 0 by pre-signup days.
  - **Health score** — reuses the Health module's own quality-aware `calculateHealthScore()` (§5: `nutrition×0.6 + activity×0.4`, checked against real BMR/TDEE-derived calorie/protein/step targets) instead of a separate presence-only formula, so eating well over a real calorie target now genuinely drops the score. Falls back to the old presence-only formula — `(anyWorkoutLoggedToday ? 60 : 0) + (metricsLoggedToday out of 4 fields / 4) × 40` — only when no `health_profile` exists yet (targets uncomputable).
  - **Finance score** — same band shape as before, smoothed within each band instead of a hard cliff: `ratio≤0.70→100`, `ratio≤0.85→linear 90→75`, `ratio≤1.00→linear 75→55`, `ratio≤1.20→linear 55→30`, else `max(10, 30−(ratio−1.20)×40)`; `60` if no budget set and zero spend logged, `50` neutral default otherwise. (v1's cliff meant crossing 90% of budget by even ₹1 cost 15 points outright.)
  - **Career score** (rebuilt 2026-10-08 with the Interviews revamp): `min(100, (profile filled?15:0) + min(30, activeInterviewProcesses×10) + min(30, mockRoundsLast30Days×6) + min(25, interviewQuestionsLoggedLast30Days×5))` — live processes (status screening/interview) plus the practice that prepares for them. Was `profile 15 + skills×2 (≤20) + active applications×8 (≤25) + quiz attempts×4 (≤20) + job-alert tracked 20`; the Topic Quiz and Job Alerts were removed.
  - **Learning score — removed 2026-10-08** with the Learning module. `life_score_logs.learning_score` is no longer written (defaults to 0); past rows keep their old value but no surface reads it (digests, Explain My Score, Monthly Review and the score history all dropped Learning).
  - **Projects/Coding score** (changed 2026-09-24): `round(volume × 0.5 + consistency × 0.5)`. **Volume** = `min(100, round(weightedCompletions × 3.2))`, `weightedCompletions = Σ` `coding_daily_questions` completed in the last 30 days, each weighted by category (`LIFE_SCORE_THRESHOLDS.codingCategoryWeight`: algorithm `1.0`, system-design `1.5`, quiz/javascript-functions/ui-coding `0.6`). **Consistency** = `min(100, round(practiceDays / codingPracticeDaysTarget (20) × 100))`, practice days = distinct IST days with a completion. Both key on `completed_at`, not `assigned_date` — the old assigned-date/volume-only formula let a 37-question bulk catch-up of August picks hold the score at 96–100 through a September with 6 practice days. Tip names the practice-day count when consistency is the weaker half. Reuses `codingHistoryForWeakAreas` — no new query.
  - Every dashboard load **upserts today's raw sub-scores + the blended `life_score`** into `life_score_logs` (one row per user per day) — since 2026-09-24 via `next/server`'s `after()` with the service client (after the response is sent, so the write no longer blocks render), and the 30-day history read runs inside the main query batch instead of as a separate sequential round-trip; together these took a warm Dashboard load from ~2.6–3.9s to ~1.6–2.0s on the local dev server
  - **Explain My Score** — clicking the Life Score ring opens a popover (`src/features/brain/components/ScoreExplainer.tsx`) showing each module's full breakdown — `"{today} today · {weeklyAvg} this week avg → {blended}"` — plus a day-over-day delta of the *blended* figure (computed by also blending yesterday's raw score with its own trailing 7 days, not by diffing raw-vs-blended) and that module's existing deterministic tip, sorted biggest movers first. Fully deterministic — no AI call. `explainScore()` (`src/features/brain/calculations.ts`) is now a thin sort/label layer — all the blending math lives in `getDashboardData()`, which passes a finished `scoreBreakdown: Record<ScoreModule, {today, weeklyAvg, blended, delta}>` in.
  - **Life Score Trend** (`LifeScoreTrend.tsx`, lazy-loaded via `next/dynamic` with `ssr: false` — recharts is a ~100KB client-only dependency used nowhere else in the app, so it's code-split out of the main bundle rather than block initial paint) — a Weekly/Monthly-toggle line chart of the Life Score, fed entirely by `scoreHistory` (30 days of `life_score_logs`, already fetched for Explain My Score above — Weekly is just its last 7 points, no new query). Its `life` line is the blended headline trend (smoother by design); the per-module lines elsewhere that read the same `scoreHistory` stay raw/spikier, since only `life_score` is stored already-blended. Deterministic, no AI.
- **Top Priority banner** — the single highest-ranked item from the same list Needs Attention renders (below), surfaced directly under the greeting rather than requiring a scroll past Quick Stats/What's Changed/Morning Brief/the Life Score hero to find it. `buildPriorityItems()` (`dashboard/priority.ts`) is the shared ranking (risks → Today's Focus signals → opportunities) both this banner and Needs Attention consume, so they can't disagree on what's most urgent. Read-only pointer, not dismissible — dismissing stays exclusive to the full Needs Attention card.
- **Daily Operating System** (Phase 5 PRD, third rewrite of this PRD file — see git history; superseded Phase 4's "Executive Dashboard" and folded its pieces in) — the Dashboard is reorganized around "what changed / what to do / what needs attention / goal progress," with everything from before still present, just repositioned rather than removed:
  - **Quick Stats** (`QuickStats.tsx`) — the PRD's "Sidebar Widget" (written when the nav was still a PRD-v2 sidebar design, since replaced by the current `TopNav` — see "Navigation structure" above), deliberately rendered as a page-level compact strip instead of living in the global nav component, which has no per-page data — fetching Dashboard-specific stats on every other page app-wide just to populate a global widget would be a wasted query everywhere else. Four stats (was five — Learning Streak removed 2026-08-21 along with study-time logging, see §6): Coding Streak (`🔥`, via `computeCodingStats()`, sub-text "today still open/solved"), Workout Streak (`🏋️`, sub-text "Logged today" / `{category} today` / "Not yet today" using the already-fetched active workout's category), Budget Remaining (today's month-to-date, 3-tier red/amber/green by % remaining; once over budget the tile reads "Budget · Over ₹X" in red instead of a "₹-X" value, and "—" / "No budget set" when there's no budget — 2026-09-24), Workout Today (done/pending). Each tile links to its module. Protein/Steps Remaining (also named in the PRD) are deliberately left out — computing them needs a new `health_profile` fetch + target calculation, a bigger lift than this widget's scope justifies. (The Goal Progress bars that used to fold in below this strip, the separate cross-module Goals card, and the 6-tile Modules grid that used to sit near the bottom of the page were all removed [Goals: 2026-08-10/11, Modules grid: 2026-08-12]; the underlying Cross-Module Goal Engine itself — `crossModuleGoals`, `goals/` — was fully removed 2026-08-11, see §12's note. `data.financialGoals` is untouched, still feeding Ask Brain's context.)
  - **What's Changed** (`WhatsChanged.tsx` + `whats-changed.ts`) — pure deterministic day-over-day deltas, no AI: Life Score Δ (vs. yesterday's `life_score_logs` row), weight Δ, a new expense/workout/application logged today. Each links to its module. On a day with nothing to show, renders as one slim inline line (no `Card` title/padding chrome) rather than a full-width card holding a single throwaway sentence.
  - **Morning Brief** (`ExecutiveBrief.tsx`) — the AI paragraph from the `daily-briefing` cron (§11), persisted to `daily_briefings` (`upsert(onConflict: user_id,date)`) so the Dashboard shows it without a fresh AI call on every page load. Shows a plain "not generated yet" state before that morning's ~8:30am IST cron has run, rather than triggering one live. Below a divider (added 2026-08-18, per the Claude Design source): a compact "Automation Rule" / "Risk" / "Opportunity" highlights strip — the single top item from each of `computeAutomationRules()`/`computeRiskEngine()`/`computeOpportunityEngine()` (`getExecutiveData()` in `executive-actions.ts`, same already-fetched deterministic data Needs Attention renders in full below), not a new query or AI call.
  - **Needs Attention** (`NeedsAttention.tsx`) — replaces the old separate "Today's Focus" card and Executive Brief's "Decision Queue," consolidated into one ranked list capped at 3 ("anything more indicates prioritization failed," per the PRD) rather than showing the same class of information across multiple cards. Risks lead (real, time-sensitive problems), then Today's Focus's existing ranked signals, then Opportunities (lowest urgency) — concatenated in that priority order via the shared `buildPriorityItems()` (which also drops a Today's Focus signal when a risk already covers the same issue — `SIGNALS_COVERED_BY_RISK` in `dashboard/priority.ts`: `budget_pace` covers `finance.over_budget`/`near_budget`, `coding_streak` covers `coding.question_pending`; added 2026-09-24 after the budget showed up twice in the 3 slots) (see Top Priority banner above), not a single merged numeric sort, since risks/opportunities and signals come from different systems. Row style restyled 2026-08-18 to match the Claude Design source: a uniform colored dot per row (risk keeps its real per-severity color — red/amber/yellow — rather than the design's flattened single red) replaces the old per-type icon/emoji, and risk/opportunity rows show a second "→ {action}" suggestion line — `Opportunity` gained an `action` field split out from its one-sentence text to match `Risk`'s existing shape. Signal rows deliberately don't get a suggestion line: the 12 signal generators across the module `signals.ts` files each write one blended sentence already, and inventing a separate action string for each risked reading as filler rather than real guidance. Risk/Opportunity items link to their module (`KIND_HREF` in `dashboard/priority.ts` maps each risk/opportunity `kind` — `budget_pace`→Finance, `protein_decline`→Health, `coding_streak`→Coding, `interview_momentum`→Career) and keep the same dismiss mechanism as before (`decision_queue_dismissals`, `useOptimistic`); signal items are plain links, not dismissible.
  - **Today's Insight** (`TodaysInsight.tsx`) — replaces the old "Insights" card (6 deterministic one-liners). Shows the single most-recently-confirmed pattern from `getRecentPatterns()` (Weekly Pattern Mining, §12) instead of a fresh per-day AI call — "one high-quality insight" satisfied with zero new AI cost. Falls back to a plain "no confirmed pattern yet" message.
  - **Evening Reflection** (`EveningReflection.tsx` + `evening-reflection.ts`) — visible from 6pm through 5am the next morning local time (this is a single-user, India-based app, so browser-local hours already serve as an IST proxy, same as the existing greeting bar's morning/afternoon/evening logic). **Fixed 2026-08-24**: the visibility gate used to be `hour < 18 → hidden`, which silently hid the section again at midnight even mid-late-night-session — extended to `hour >= 18 || hour < 5` so a genuinely late night doesn't lose it. Past midnight, the section reflects on *yesterday* rather than the just-started, nearly-empty new calendar day: the client passes `isLateNight` (computed from the same local-hour check) down through `getEveningReflection()` → `generateEveningReflection()` → `gatherTodayActivityLines(db, userId, daysAgo)`, which now takes an explicit `daysAgo` (0 = today, the default the Daily Auto Journal cron always uses; 1 = yesterday, only ever passed by the late-night case here). A separate on-demand AI narrative from Daily Auto Journal's 11pm cron (different purpose: this is a same-evening check-in, that's an end-of-day recap needing to run after even a late coding session) — reuses the journal's activity-gathering (`gatherTodayActivityLines()`, a shared helper). Routes through the gateway as `evening_reflection` (Sonnet, 6h cache). Fetched only after the time gate passes, so it never blocks initial page load. (A deterministic "Tomorrow's top priority" line — the top pending Planner task — sat below the paragraph until the Planner module was removed on 2026-10-07; the AI prompt still tells it not to invent plans for tomorrow.)
  - **Today's Schedule** (a real 09:00/12:30-style unified timeline) is the one Phase 5 PRD section deliberately not built — it needs Calendar integration (out of scope, see Phase 3), and without real clock-times the only available data would just repeat Today's Mission's items.
- **Gamification — removed from the hot path (2026-08-20).** Total XP (`life_score` summed over the trailing 365 days), 9 level thresholds, a day-streak counter, and 9 badges were computed and upserted into `user_xp` on every single Dashboard load despite the Level/XP card having been removed from `DashboardView.tsx` earlier — a real write on the highest-traffic page for a UI element nobody could see. The computation and the `user_xp` upsert were deleted from `getDashboardData()`; the `user_xp` table itself is untouched (still read by Settings' Data Export) and could be recomputed and re-wired to a real UI element later if wanted, but nothing currently does. The `scoreHistory` query it used to sit alongside is unaffected — Life Score Trend still needs it for its `life` column.
- **Daily Mission card** — deterministic (no AI), separate from Life Score: a fresh checklist that resets every midnight, distinct from Life Score's blend of persistent module state (month-to-date budget, 30-day coding activity, career profile completeness, etc.). Items (`src/features/dashboard/daily-progress.ts`): today's health metrics logged (weight/calories/protein/steps); today's workout, only counted if one is currently assigned, done on completed *or* skipped; **one Coding item** — "Coding practice — finish 1 of today's picks (x/N done)", over every active pick (§7, carried-over included), done once any pick is completed today (merged 2026-09-24 from four separate algorithm/quiz/JS-function/UI-coding items, which made coding 4 of ~8 items and decided the mission on its own); an expense logged today (the daily-read item went with Learning, 2026-10-08). (Planner tasks due today were items here until Planner was removed 2026-10-07. A "study session logged today" item existed here until 2026-08-21, when study-time logging was removed entirely — see §6.) Score = `round(completed/total × 100)`, or `100` if nothing applies today (not a `0/0`). Renders as a compact ring + the full checklist (`todayProgress.items`, not a filtered subset) as direct links to their module, done items shown with a green dot and strikethrough text rather than hidden — seeing the day's wins matters as much as seeing what's left. (Named "Today's Progress" until Phase 2's Brain PRD reframed the same primitive as "Daily Mission" — no logic changed, just the label. The older "show only up to 5 unclosed items" behavior and its `getTodayRecommendations()` helper were removed 2026-08-10 in favor of showing the full list with completed items struck through.)
- **Ask Brain** — a conversational AI advisor registered on the Dashboard's header trigger (`src/features/brain/components/BrainAdvisorTrigger.tsx` → `BrainPanel.tsx`), same "AI advisor header architecture" pattern every other module uses. The panel has four tabs:
  - **Ask** (`BrainChat.tsx`) — multi-turn free-form Q&A; prior exchanges in the session are replayed into each new prompt for continuity (not persisted across page loads). Routes through the gateway as the `brain_qa` task (Sonnet, uncached).
  - **Decide** (`DecisionHelper.tsx` + `DecisionCard.tsx`) — one-shot structured decision support ("Should I switch jobs?", "Can I afford a car?"). Routes through the gateway as the `brain_decision` task (Sonnet, uncached), returning strict JSON (`{decision, reasoning, tradeoffs[], confidence, actionItems[]}`) parsed with the same regex-extract + try/catch fallback pattern `recommendations.ts` uses, defaulting to a "couldn't reach a decision" card on any parse failure rather than erroring.
  - **Reflect** (`WeeklyReview.tsx`) — Weekly Reflection, generated on demand when the tab is opened (not a Sunday-only cron artifact): `getWeeklyReflectionContext()` re-runs the same trailing-7-days `life_score_logs` query the Telegram weekly digest already does, through a shared `computeScoreStats()` helper (`src/features/ai/score-stats.ts`, extracted so both surfaces agree on the numbers), plus confirmed patterns from `getRecentPatterns()`. Renders the per-module score bars + best/worst day (`ScoreStatsSummary.tsx`, shared with Monthly below), then one AI-written paragraph (`brain_weekly_reflection` task, Sonnet, 6h cache) covering wins/misses/patterns/lessons/next-week's-focus/risk-areas in prose, grounded only in those numbers. Returns a static "not enough data" string with no AI call when fewer than 2 days are logged that week.
  - **Monthly** (`MonthlyReview.tsx` + `MonthlyReviewCard.tsx`) — Monthly Executive Review, same on-demand pattern over a trailing 30 days instead of 7. `getMonthlyReviewContext()` reuses `computeScoreStats()` plus a new `computeCategoryTotals()` helper (also extracted into `score-stats.ts`, shared with the Telegram digest's spend formatting) for this calendar month's top spend category; Career/Finance-total/Coding figures are read from the already-built `BrainContext` passed in rather than re-queried. Routes through the gateway as `brain_monthly_review` (Sonnet, 6h cache), returning strict JSON (`{career, finance, health, learning, coding, overall, biggestAchievement, biggestMistake, recommendation}`, each field 1-2 sentences) rendered as labeled rows — a structured card rather than Reflect's single paragraph, per the PRD's stated shape for this one. Returns a static "not enough data" response with no AI call when fewer than 5 days are logged that month.

  All three tabs share the same today-snapshot context: `src/features/brain/context-builder.ts` is a pure reshape of this same `getDashboardData()` output into the Phase 2 PRD's stated context shape — no duplicate queries. Reflect alone fetches its own extra 7-day history since that snapshot doesn't carry it. Every system prompt here explicitly forbids inventing facts not present in the context and (for Ask/Reflect) forbids markdown formatting (see §12).
- **Today's Focus signals** (feed into Needs Attention above, no longer their own card) — deterministic ranking (no AI): an interview round within 48 hours (95, 📅, `checkUpcomingInterview()` — "{company} {round} round today/tomorrow — prep for it now"), over-budget this month (80, 💸) or ≥90% of budget used (55, 💸), today's coding question still open (65, 💻), today's workout still open (60, 🏋️), no health metric logged today (50, 📊), a Coding weak topic (48, 🧩, `checkCodingWeakArea()` — reuses the same `computeWeakAreas()` Coding's own recommender uses), a solved coding question not re-solved in 14+ days (40, 🔁, auto-detected complement to §7's manual `needs_revision` flag — dedupes by question so a recently re-solved question isn't flagged from an old row), a company mid-process (phone screen / interviewing) with no round scheduled (58, 🎯, `checkUnscheduledProcess()`). (The interview-stage (90), Career-quiz weak subtopic (48), quiz-revision (42) and Job Alert (55) signals were replaced 2026-10-08.) Each candidate is produced by its own module's `signals.ts` (e.g. `src/features/finance/signals.ts`) as a `Signal`, aggregated and ranked by `src/lib/signals.ts`'s `rankSignals()` — a shared layer per Product Principle 4, rather than one hardcoded candidate list. (The old "Insights" card — budget remaining/over, low sleep, active-application/pending-task/in-progress-learning counts — was replaced outright by Today's Insight above rather than kept alongside it. The overdue-task (100) and high-priority-task (70) signals went with the Planner module, 2026-10-07.)
- **Recent bot activity** — last 50 rows from `telegram_logs`, rendered as compact single-line rows (emoji + module + `"user message" → first line of bot reply`, quoted and arrow-joined into one truncating span per the Claude Design source, same on mobile — no separate reply column to hide — + relative time), paginated client-side 10 at a time; header shows today's/month's AI spend (`$0.0047`-style 4-decimal formatting for sub-cent amounts) and a cache-hit-rate tooltip.
- **Module Scores** — 4 mini progress rings (Health/Finance/Career/Coding; Learning removed 2026-10-08), each ring colored by its score tier (green ≥70, amber ≥45, red below — 2026-09-24; was a fixed color per module, so Coding was always red even at 92), each with a deterministic tip naming the single highest-point-value gap for that score (e.g. "No workout logged today — worth 60% of this score") — computed from the same sub-components the score itself is built from, no AI. The tip shows twice: truncated to one line under the ring always, and in full on hover via a styled tooltip (not a native `title` attribute — needed its own theme-aware background/text so it stays readable in light theme too). (The 6-tile Modules grid that used to sit below Recent Bot Activity was removed 2026-08-12 — Quick Stats and Module Scores already surface the same per-module signal higher up the page, so the grid was redundant. `overdueCount`, originally added to `getDashboardData()`'s `stats` return to feed that grid's second-clause stat lines, is still used by Needs Attention. `resourcesNeedingRevision` — the other stat added for the same purpose — was removed 2026-08-21 along with study-time logging and the revision auto-re-add feature it depended on, see §6.)
- **Quick Add** — floating "+" button for fast Expense / Metric entry without leaving the dashboard (the Task option went with Planner, 2026-10-07).
- Realtime refresh: subscribes to Supabase Realtime changes on `workouts`, `health_metrics` and debounce-refreshes the page (e.g. after logging via Telegram).

## 3. Interviews (`/career`) — revamped 2026-10-08

Career is now an **Interviews** module (nav label "Interviews", route unchanged) for the War Mode job hunt: applications themselves aren't tracked (you apply to hundreds elsewhere) — a company is added **only once a phone screen is booked**, then prepared for specifically, and every question the interviewers ask is kept. Tabs (`PageTabs`): **Companies** / **Question Log** / **Profile**. Removed 2026-10-08: the Applied stage + status filter, the per-application card row, **Job Alerts** (the `job-alerts` cron, `job-alerts.ts`, the web feed and its Telegram alerts; `job_alerts_seen` kept, unused) and the **Topic Quiz** (`ai/quiz.ts` with the `generate_topic_quiz`/`recommend_quiz_topic` AI tasks, `quiz-calculations.ts`; `quiz_attempts` kept, unused — Prep's Question Bank + AI ratings replace it, and Prep readiness no longer reads it).

- **Companies** (`applications` rows): company, role, stage (`STAGE_CONFIG`: Phone screen `screening` → Interviewing `interview` → Offer / Rejected / Withdrawn; `applied` only on old rows), optional job link, optional job description, notes. Add via the Add company modal (company, role, stage, link, JD, notes) or the Career bot. Sorted active first, then by next scheduled round.
- **Rounds** (`interview_rounds`): kind (`ROUND_KINDS`: recruiter, phone screen, technical, coding, system design, behavioral, hiring manager, onsite/final, other), date-time (IST display), interviewer, status (scheduled / done / cancelled), outcome (pending / passed / failed), notes. Adding a round past the phone screen moves a `screening` company to `interview`.
- **Questions asked** (`interview_questions`) — the interview experience, kept: the question (exact wording), category (`QUESTION_CATEGORIES`: technical, coding, system design, behavioral, AI-native, other), round, your answer (refine it over time), how it went (well / ok / badly), notes. Logged per company or via the Career bot; the **Question Log** tab lists all of them across companies with category chips, a "Went badly" filter and search.

- **Money Advisor** (`finance-advisor.ts`) — opened from the header trigger (see "AI advisor header architecture" under Architecture), two tabs:

- **Calculations** (`calculations.ts`, pure functions, no AI):
  - **BMI** = `weightKg / (heightCm/100)²`
  - **BMR** (Mifflin-St Jeor): `10×weightKg + 6.25×heightCm − 5×age`, `+5` for male / `−161` for female
  - **TDEE** = `BMR × activity multiplier` (`sedentary 1.2, light 1.375, moderate 1.55, active 1.725, very_active 1.9`)
  - **Normal-BMI target weight** = `24.9 × (heightCm/100)²` (upper bound of the normal BMI range — the most achievable target for someone starting overweight, auto-computed from height, no manual entry)
  - **Daily targets** (`calculateDailyTargets`): if current weight puts BMI above 24.9, calorie target carries a modest deficit (`0.4–1kg/week`, scaled to how much is left to lose) toward the normal-BMI weight; otherwise it's maintenance. `dailyCalorieTarget = max(1500, round(TDEE − deficit))`. **Protein target is based on the normal-BMI target weight while cutting, not current scale weight** (`2g × targetWeightKg`) — standard fat-loss guidance, since 2g/kg of an overweight starting weight overshoots real need. Fat = `25% of calorie target ÷ 9`, carbs = remainder `÷ 4`.
  - **Health Score (0–100)**: `nutrition×0.6 + activity×0.4` — nutrition blends calorie-accuracy and protein-hit-rate 50/50 (0 if nothing logged); activity blends step-target-% with a workout-today bonus/floor. Each sub-score carries a plain-English reason naming whichever factor is actually worse that day (changed 2026-08-20 — nutrition's reason used to always name the protein gap regardless of which one was further off, since protein's target is high enough that its gap was almost always >20g and permanently won; now it compares `calScore`/`proteinScore` directly and shows the lower one's issue, e.g. "Calories are 63% off target" surfaces correctly when that's the bigger miss). No sleep component (removed).
- **Weight Trend** (2026-09-24, `WeightTrendCard.tsx` + `computeWeightTrend()` in `calculations.ts`) — replaces the old README claim of a `HealthTrend.tsx` chart, which no longer exists in the code. Hover/tap shows date + value with a crosshair. Needs ≥3 weigh-ins spanning ≥7 days, otherwise a prompt. Deterministic, no AI.
- **Activity-level check** (2026-09-24, `suggestActivityLevel()` in `calculations.ts`) — compares the profile's `activity_level` (which drives TDEE, hence the calorie target) against the last 28 days of real data: workout days/week from the Workout Calendar (the `workouts` table) and average steps over logged days (needs ≥7), banded the same way `ACTIVITY_LEVELS`' labels describe (light 1-3 days/week, moderate 3-5, active 6+), bumped one level at ≥10k avg steps. When they disagree, the Health Score card shows a one-line notice ("Profile says Active; last 4 weeks look Light (1.8 workouts/wk, ~6,227 steps) → target 1746 kcal") with an **Update** button that saves only `activity_level` via `upsertHealthProfile()`. Added after an audit found the profile set to Active (×1.725 → 2,471 kcal target, projecting ~1 kg/week loss) while real data showed ~1.8 workouts/week and ~0.26 kg/week actual loss.

## 10. Telegram bot — the interaction layer

Each module is its own Telegram bot (own `TELEGRAM_BOT_TOKEN_*`), plus the **Daily** bot (module key `planner`, `TELEGRAM_BOT_TOKEN_PLANNER` — the former Planner bot, kept under its old key so its registered webhook URL `/api/telegram/planner` keeps working), all pointed at one webhook (`src/app/api/telegram/[module]/route.ts` → `src/features/telegram/handler.ts`).

**Processing pipeline:**

1. Only messages from `TELEGRAM_ALLOWED_CHAT_ID` are accepted (single-user, single-chat system).
2. A daily AI-call cap (`TELEGRAM_DAILY_AI_CAP`, default 300) counted from `telegram_logs` protects against runaway spend — once hit, the bot replies with a quota message and skips processing entirely for the rest of the day. Separately, the Gateway's own dollar budget (§12) reserves a slice of the daily *and* monthly spend exclusively for `telegram_intent`/`telegram_vision` — if that reserve check fails, the handler replies `⏸️ AI budget for today is used up — resets at midnight IST` (daily ceiling) or `⏸️ AI budget for this month is used up — resets on the 1st` (monthly ceiling, worded separately since it doesn't reset tonight) and logs `{"action":"budget_exhausted","scope":"daily"|"monthly"}`, distinct from the `{"action":"help"}` cheat-sheet reply below (added 2026-09-23 after a `recommend_daily_read` web-search call alone exhausted a full day's budget and every bot silently fell back to the help menu, indistinguishable from a real parsing miss).
3. **Voice messages** are transcribed first via Groq's `whisper-large-v3-turbo` (needs `GROQ_API_KEY`) before anything else happens.
4. **Photos** are supported by Finance (receipt → extracts amount + category) and Health (meal photo → estimates calories + protein) via a per-module `VISION_PROMPT`; other bots reply that photos aren't supported yet.
5. The transcribed/typed text (or image) goes to Claude with a module-specific system prompt defining a JSON action grammar, plus the actual current date injected (so "today" never relies on the model's training cutoff). A single message can produce **multiple actions** (e.g. a voice note describing a workout, water, and a finished chapter all at once) — the model returns a JSON array instead of one object, and each is executed and replied to in turn.
6. Claude's response is parsed and dispatched to that module's `execute()`, which does the real Supabase read/write and formats a Markdown reply.
7. Every interaction (module, chat id, message, parsed action(s), reply) is logged to `telegram_logs`, non-fatal on logging failure.

**Cross-cutting bot features:**

- **Undo/amend**: every bot supports `undo_last` (deletes/reverts the most recent write for that module — expense, application, ad-hoc workout log, resource, or coding-question/reading completion); Finance additionally supports `amend_expense` (corrects just the amount on the most recent expense).
- **Reminders**: the Daily bot can `set_reminder`/`list_reminders`/`delete_reminder` (writes the `reminders` table used by Settings, §9).
- **Inline buttons**: every "add" action across 3 bots — Career, Finance, Health (application, expense, loan, investment, ad-hoc workout log) — also attaches an "↩️ Undo" button (`src/lib/telegram/buttons.ts`); Coding and Astrology don't attach one (Coding's `complete_question`/`undo_last` and Astrology's read-mostly command set have no equivalent "add" action to undo). Unlike the `undo_last` text command, which always targets the most-recently-created row, the button encodes the specific row's id in its `callback_data`, so tapping it later (after newer items were added) still undoes the correct one, not whatever's newest at tap time. An explicit table allowlist (`UNDOABLE_TABLES`) guards the generic `undo:<table>:<id>` callback handler in `handler.ts` against acting on an unexpected table.
- **Proactive budget nudge**: logging an expense via Finance checks that category's budget and appends a warning if it's now over or ≥90% used.

## 12. AI Gateway

Every AI call in the app funnels through one function: `askAI(task, prompt, system?, opts?)` in `src/lib/ai-gateway.ts`. No feature module calls Anthropic directly (`src/lib/anthropic.ts`'s `callClaude()` is a low-level primitive only the gateway imports). This is Product Principle 3 made concrete. `askAIWithMeta()` (added 2026-08-20) is the same gateway logic returning `{text, generatedAt}` instead of a bare string — `askAI()` is just a one-line wrapper around it that discards `generatedAt`, so every pre-existing call site is unaffected. Only the 3 call sites that display a freshness timestamp on cached AI content (Career's Recommended Topic and Interview Guidance, §3; Astrology's Characteristics, §13) use the `WithMeta` variant directly.

- **Model routing** — a fixed per-task table picks the model. Only `telegram_intent` routes to Haiku (`claude-haiku-4-5`); every other task (`telegram_vision`, `career_mentor`, `jd_analysis`, `company_insights`, `finance_advisor`, `health_report`, `health_daily_plan`, `health_advisor`, `study_plan`, `resource_quiz`, `recommend_resources`, `recommend_daily_read`, `coding_mentor`, `recommend_coding_questions`, `module_recommendations`, `daily_briefing`, `weekly_digest`, `monthly_digest`, `brain_qa`, `brain_decision`, `brain_weekly_reflection`, `brain_monthly_review`, `daily_journal`, `finance_scenario`, `evening_reflection`, `estimate_food_nutrition`, `astrology_reading`, `astrology_characteristics`) routes to Sonnet (`claude-sonnet-4-6`). (`doc_qa`/`doc_summary` were removed with the Documents module, §8 — no longer real tasks.)
- **Response caching** — `ai_cache` table, key = `sha256(model::system::prompt)`. A changed prompt (i.e. changed underlying data) naturally busts the cache. Per-task TTLs range from none (always fresh, e.g. Q&A/decision/scenario tasks whose prompt genuinely differs per call) up to a full year (`astrology_characteristics` — effectively permanent, since its prompt only changes when the natal chart itself does, §13); `company_insights`/`estimate_food_nutrition` use 7 days (nutrition facts for the same item+quantity don't change, so a repeat like "200g chicken breast" is a cache hit); images are never cached. A cache hit skips the API call entirely and logs zero cost. Per CLAUDE.md's "minimize Anthropic API usage" guidance, every cron-generated narrative/digest task (`daily_briefing`, `weekly_digest`, `monthly_digest`, `daily_journal`) uses a 6h TTL rather than none — most have an on-demand Telegram duplicate (e.g. "how am I doing" re-running `daily_briefing` the same morning the cron already sent it) that would otherwise re-spend an API call for byte-identical output. **`astrology_reading` is the one task whose TTL isn't a fixed `TASK_CONFIG` constant** — `askAI`'s `opts.cacheTTLSeconds` can override the task's default per call, and `astrology/actions.ts` computes it dynamically per request: seconds until the next IST midnight for `daily`, until the 1st of next month for `monthly`, until next Jan 1 for `yearly` — so a reading caches until its own calendar period actually ends, not a flat duration, and a repeat request (web reload, or the Telegram bot/cron's own same-day call) costs zero extra spend for the rest of that period.
- **Budget enforcement** — `ai_usage_logs` logs every call (task, model, tokens, `estimated_cost_usd`, cache-hit flag). Before calling the model, the gateway sums today's and this month's spend (fail-open on a spend-lookup error itself — treated as $0 spent rather than throwing, so a transient DB blip can't block every AI call in the app); if either meets `AI_DAILY_BUDGET_USD` (default $3) or `AI_MONTHLY_BUDGET_USD` (default $50) — scaled down for non-interactive tasks, see the reserve below — it skips the API call and returns that task's configured fallback string instead. `askAI()` also wraps the actual API call itself in a try/catch (`ai-gateway.ts`) — **any** failure (budget, API error, network) returns the same configured fallback rather than throwing, so no page or cron job can ever break from an AI call failing; structured-output tasks fall back to `'[]'`/`'{}'`/`'{"action":"help"}'` for silent degradation, a few user-facing Q&A tasks (`career_mentor`, `finance_advisor`, `health_advisor`, `coding_mentor`, `brain_qa`, `finance_scenario`) return an explicit "I'm over my AI budget for today" message, and every "always send" cron-generated narrative (`daily_briefing`, `weekly_digest`, `monthly_digest`, `daily_journal`, `evening_reflection`) has an explicit one-line "AI summary/reflection/journal unavailable" fallback (changed 2026-08-20, was an empty string — a real Sonnet failure on one of these used to silently leave a blank gap in an otherwise-fine message rather than saying anything). **Interactive-task reserve** (added 2026-09-23): `telegram_intent`/`telegram_vision` are checked against the full daily *and* monthly budget, but every other task is checked against only 70% of each (`INTERACTIVE_RESERVE_FRACTION`) — so a background cron/on-demand task spending unevenly earlier in the day, or across the month, can use up to that 70% before it starts getting blocked, but can never fully starve someone actively texting a bot. `askAIWithMeta()`'s result also now carries `budgetExhausted` plus which ceiling actually tripped (`budgetScope: 'daily' | 'monthly'`) so a caller (the Telegram handler) can tell "budget ceiling hit" apart from "missing userId" or "API error" (which all previously collapsed into the same fallback string with no way to distinguish them), and can word its message correctly — a monthly cutoff resets on the 1st, not at midnight, so the handler shows a different reply for each scope instead of one `{"action":"help"}` cheat-sheet or a message that wrongly promises the bot is back by midnight. No task grants Claude the server-side `web_search` tool (removed 2026-09-23 along with the `AskAIOptions.webSearchMaxUses`/`callClaude` plumbing that enabled it — a single search call had been observed returning 80k+ input tokens, enough alone to blow a day's budget, with no way to cap how much a search returns, only how many run); every task that used to verify a URL via search (`recommend_daily_read`, `recommend_resources`) now has the model self-report instead, null when unsure.
- **Rule-engine-first**: score math, sorting, chart data, and the coding rotation are all deterministic wherever possible, per Product Principle 2.

**AI feature files** (`src/features/ai/`), all going through the gateway: `career-mentor.ts`, `finance-advisor.ts`, `health-report.ts` (includes `askHealthCoach`, the Health bot's free-form Q&A), `coding-mentor.ts` (the Coding bot's free-form Q&A — recent streak/solved-questions/readings as context), `weekly-digest.ts`, `recommendations.ts` (the generic recommendations widget behind Code Mentor and half of Health Coach — wired into Health and Coding only; Career and Finance have a dedicated mentor/advisor instead). (`executive-summary.ts` was removed with the Planner module, 2026-10-07.)

**Personal Brain** (`src/features/brain/`, Phase 2 PRD, cross-module rather than per-module): `context-builder.ts` reshapes `getDashboardData()`'s existing aggregate query into the PRD's stated context shape (no new queries beyond the two below); `calculations.ts` has `explainScore()` (deterministic, feeds Explain My Score above); `prompts.ts` + `advisor.ts` have `askBrain()` (the `brain_qa` task) and `askBrainDecision()` (the `brain_decision` task, strict-JSON structured output), feeding Ask Brain's Ask/Decide tabs above; `advisor.ts`'s `getWeeklyReflection()` is self-contained (creates its own supabase client + `auth.getUser()`, unlike the two above which take an already-built context prop) and feeds the Reflect tab; `getMonthlyReview(context)` takes the caller's `BrainContext` for its Career/Finance-total/Coding fields but is otherwise self-contained the same way, feeding the Monthly tab — see the Ask Brain entry above for what both do.

- **Pattern Detection** (`signals.ts`) — deterministic-only checks (Product Principle 2; AI is never used to compute a pattern, only to narrate one elsewhere) run weekly from the `weekly-digest` cron, four so far (Phase 3 PRD's "Weekly Pattern Mining"): workout day-of-week concentration (≥40% of last 90 days' workouts on one weekday, min. 3); a weekend protein drop (weekend avg <75% of weekday avg, needs ≥4 weekday + ≥2 weekend logged days); coding time-of-day skew (≥65% of the last 60 days' solves in one half of the day, min. 6, using `toISTHour` on `coding_daily_questions.completed_at`); and a workout→same-day-coding correlation (coding completion rate on workout days is ≥20 points higher than on rest days, min. 4 days each side). (A fifth pattern, sleep→next-day-coding correlation, was removed 2026-08-13 along with the rest of Sleep tracking — see §5.) Three more of the PRDs' example patterns (overspend-after-salary, interview-performance-vs-sleep, workout-drop-during-travel) are explicitly left out because they need data no integration currently provides (a real salary-*credit* event, interview outcomes, travel/calendar detection — Calendar/Gmail/GitHub integrations aren't planned, see `PRDs/phase3.md`'s git history for why). Matches persist to `brain_patterns` (see Database) via `upsert(onConflict: user_id,pattern)`, incrementing `times_confirmed`/`last_seen` on repeat detection so patterns genuinely accumulate rather than reset each run. `context-builder.ts`'s `weeklyPatterns` only surfaces patterns confirmed more than once (`times_confirmed > 1`) and seen in the last 30 days, so a one-off fluke isn't presented as an established pattern. `monthlyPatterns` stays an empty placeholder — no monthly-cadence pattern job exists yet.
- **Memory** — rather than a new store (Core Principle 1: the Brain never owns data), `career_profile`'s existing `current_role`/`current_company`/`target_role`/`current_salary` columns are read straight through into the context (the `career_profile` query in `getDashboardData()` was widened to select these, no new query). **Memory Evolution** (Phase 3 PRD) widened this further with Goals: `getDashboardData()` now also queries `financial_goals` (name, target/current amount, target date), threaded through as `BrainContext.finance.goals` and surfaced in Ask Brain's Ask/Decide context and Monthly Executive Review's — e.g. asking "what are my financial goals" correctly cites the real ₹ amounts and % progress, never invented ones. **Executive Memory** (Phase 4 PRD) added one more field the same way rather than inventing new speculative ones (investment philosophy, personality traits, etc. — none of the PRD's other example fields have a natural home or any feature that would actually consume them, so they were deliberately skipped): `career_profile`'s existing "Bio / Focus" free-text field (already editable on the Career page, previously never read by the Brain) is now included in `BrainContext.career.bio` and surfaced in `buildContextSummary` — e.g. asking "what's my career focus" now correctly reflects whatever the user actually wrote there.
- **Goal Engine — removed entirely (2026-08-11).** Originally a Phase 4 PRD feature: cross-module goals for Career/Learning/Coding (`src/features/goals/`, a *separate* `goals` table from `financial_goals`, which kept its own UI throughout). Its UI (`GoalsCard.tsx` and the write actions `addGoal`/`updateGoalProgress`/`toggleGoalAchieved`/`deleteGoal`) was deleted 2026-08-10, leaving only read paths (`getGoals()`, `resolveAutoMetric()`, `checkGoalProgress()`, `crossModuleGoals` threading into Ask Brain) with no way to ever create a new goal — a personal-backlog audit flagged this as "silently half-alive" (no usable feature, just dead weight in every page load that touched it), and the decision was to rip out the remaining code rather than resurrect a minimal add-goal UI. Removed: the whole `src/features/goals/` directory, `checkGoalProgress`'s Today's Focus signal, `crossModuleGoals` from `BrainContext`/`getDashboardData()`/`buildContextSummary`, and the `goalsContext` parameter (and its prompt text) from `recommendQuizTopic`/`recommendCodingQuestions`. ## 13. Astrology (`/astrology`) — added 2026-08-13, expanded 2026-08-14 (twice)

A Vedic (sidereal) horoscope module — the one module whose core output is real astronomical
calculation, never AI. Per Product Principle 2, Claude only narrates already-computed
positions; it never generates a chart itself (an AI asked to "produce a horoscope" from
scratch would hallucinate planetary positions, unacceptable for something presented as a real
chart). Origin doc: `astrology.md` at the repo root — this section is the current source of
truth for what's actually built. Built in four passes: an initial MVP (natal chart, Vimshottari
Dasha, daily reading); expanded to match a fuller Claude Design mock (Yogini Dasha,
monthly/yearly readings, Remediation); a scope increase adding Panchang, Gochara transit
analysis, the Navamsa (D9) divisional chart, a Dashboard strip, a dedicated Telegram bot + daily
cron, and a Hindi (EN/हिं) language toggle; then a further scope increase the same week adding
Chandrashtama detection, an astrology-derived daily mood forecast, a one-time Characteristics
profile, a structured daily-reading breakdown (Favorable For / Avoid / Mood Forecast /
Remediation, not just prose), and Choghadiya time-blocks. The one item `astrology.md` scoped
and then explicitly dropped mid-build (an Outcome Journal — logging how a reading's predictions
actually played out) was removed cleanly before any migration for it was applied;
compatibility/matching charts and Muhurta lookups remain explicitly out of scope.

- **Ephemeris** (`src/features/astrology/ephemeris.ts`) — `swisseph-wasm`, a WebAssembly build
  of the real Swiss Ephemeris C library. Chosen over native `swisseph` bindings specifically to
  avoid Vercel serverless native-binding deploy risk (this project has never shipped a native
  dependency); chosen over a pure-JS Meeus/VSOP87 approach (`astronomia`) for genuine
  professional-grade precision. Sidereal correction uses Swiss Ephemeris's built-in Lahiri
  ayanamsa mode (`set_sid_mode(SE_SIDM_LAHIRI, 0, 0)` + `SEFLG_SIDEREAL`), not a manual
  ayanamsa subtraction — validated at implementation time by reproducing the widely-published
  Lahiri ayanamsa value at J2000.0 (2000-01-01 12:00 UT ≈ 23.85°; this pipeline returns
  23.8571°). `next.config.ts` has two entries just for this dependency: `outputFileTracingIncludes`
  explicitly bundles `node_modules/swisseph-wasm/wasm/**` into the `/astrology` serverless
  function (the package loads its `.wasm`/`.data` files via a runtime filesystem path Vercel's
  file-tracer can't discover through static analysis alone), and `serverExternalPackages:
  ['swisseph-wasm']` keeps the package out of webpack's bundling entirely (webpack was breaking
  the package's `await import('node:module')` call for `createRequire`, throwing
  "createRequire is not a function" — reproduced locally, fixed by this config, both real bugs
  caught during implementation, not anticipated by the original doc).
- **Chart calculation** (`src/features/astrology/chart-calculations.ts`, pure functions, no AI,
  same pattern as Health's `calculations.ts`) — rashi (sign) + nakshatra + pada from sidereal
  longitude, whole-sign house placement from the Lagna, and two dasha timelines, both computed
  once at profile save via `upsertAstrologyProfile()` and stored in `natal_chart` jsonb (never
  recomputed on read, so they can't silently drift):
  - **Vimshottari Dasha** — the primary/default system, a 120-year cycle across the 9 classical
    grahas (Sun/Moon/Mars/Mercury/Jupiter/Venus/Saturn/Rahu/Ketu, not the outer planets Western
    astrology adds), keyed off the Moon's birth nakshatra, both Mahadasha and nested Antardasha
    periods.
  - **Yogini Dasha** — a secondary, shorter 36-year cycle across 8 Yoginis, also keyed off the
    Moon's birth nakshatra but with its own lord order/year-lengths and starting-point formula
    (`(nakshatraNumber + 3) mod 8`, the classical Devi Bhagavata formula). Single-level only, no
    antardasha subdivision. Verified 2026-08-18 against the full published 27-nakshatra →
    starting-Yogini table (cross-checked via three independent sources) — this surfaced a real
    bug: the formula previously had an erroneous extra `× 2` (`(nakshatraNumber × 2 + 3) mod 8`),
    which produced the wrong starting lord for every chart. Fixed as part of this verification.
- **Natal chart display** — a North Indian style kundli (`KundliChart.tsx`, SVG): fixed house
  positions (house 1 always the top-center diamond, numbered counter-clockwise), planets
  placed by house with standard 2-letter abbreviations, rashi number shown per house. The
  design mock's own natal-chart card used a simplified 3×12 grid with a footnote explicitly
  saying "production renders a true North Indian diamond kundli" — this SVG is that production
  version, so it was kept as-is rather than downgraded to match the grid literally.
- **Current Dasha strip** — accent-tinted banner showing the active Vimshottari
  Mahadasha/Antardasha + until-date (`getCurrentDasha()`, looked up against today's date, not
  recomputed) with the active Yogini period as a secondary line, right-aligned
  (`getCurrentYogini()`).
- **Horoscope** — a Today/This Month/This Year tab switcher. All three periods read the same
  current-transit snapshot (this module doesn't compute a forward window of planetary movement)
  — only the prompt's framing changes, the same way a monthly financial digest still runs off
  today's numbers rather than projecting the month. The AI prompt contains only computed
  positions/dasha state, never raw birth data. **Daily is structured, not prose**: a one-line summary
  (prompt tightened 2026-09-24 for crisp output: summary ONE sentence ≤20 words, 2–3 favorable and
  1–2 avoid phrases of 3–8 words with no explanations, mood ONE sentence ≤15 words; monthly/yearly
  prose = exactly 4 sentences ≤15 words each, <70 words; characteristics = exactly 5 sentences ≤16
  words each, <90 words — shared by web and Telegram, each prompt change regenerated once), then — matching the Claude Design source's exact layout (pulled and matched
  2026-08-14) — a side-by-side 2-column grid (green Favorable-For card / red Avoid card, each a
  bulleted list, not chip pills) and a Mood Forecast card below it with a conditional ⚠
  Chandrashtama warning line rendered off the deterministic `isChandrashtama` flag (decoupled
  from whatever the model's own mood prose says — the warning is UI-driven, not text-matched).
  From `getStructuredDailyReading(profile, lang)` — the model returns strict JSON
  (`{summary, favorableFor, avoid, moodForecast}`, parsed with the same regex-extract +
  try/catch + graceful-fallback pattern `brain_decision` already uses elsewhere); `remediation`
  is filled in afterward from the same curated `getRemediation()` table the standalone
  Remediation card uses (kept on the `DailyReading` type for the Telegram bot's flattened prose,
  but the design mock doesn't repeat it inside this card — the standalone Remediation card below
  is the only place it renders on the web page, avoiding the duplication an earlier draft had).
  **Monthly/yearly stay prose** (`getAstrologyReading(profile, period, lang)`) — "avoid X today"
  and a Moon-transit mood forecast don't translate to a month/year scale the same way. Both
  functions share one `buildReadingContext()` helper for the ephemeris/gochara/dasha work so
  they can't drift out of sync with each other, and both go through the same `astrology_reading`
  AI task (§12) — calling `getAstrologyReading(profile, 'daily', lang)` (e.g. from the Telegram
  bot or the daily cron) internally calls the same `getStructuredDailyReading` and flattens its
  JSON into readable prose, so a web-page view and a same-day Telegram request hit the identical
  cache entry rather than double-spending.
- **Remediation** — up to 3 traditional remedies for the chart's Saturn/Rahu/Ketu/Mars/Moon
  placements, sourced from a curated per-planet template table
  (`src/features/astrology/remedies.ts`) parameterized with each planet's actual house number.
  Deliberately **not** an AI Gateway call at all — narration is template text substitution, not
  free-form generation, per `astrology.md`'s explicit anti-hallucination requirement for this
  feature ("not left to the model to invent").
- **Birth Details card** — compact inline-editable field grid matching Career Profile's density
  (not a standalone form card), since birth details are effectively write-once. Unlike Career's
  per-field independent saves, every field here saves together in one submit — the natal chart
  is a function of all of them at once, so editing just one in isolation would leave the stored
  chart inconsistent with the rest.
- **Panchang** (`src/features/astrology/panchang.ts` + `panchang-actions.ts`) — the daily Hindu
  calendar: tithi (+ paksha), nakshatra-of-the-day (distinct from natal nakshatra), yoga,
  karana, sunrise/sunset, and the three inauspicious windows (Rahu Kalam, Yamaganda, Gulika
  Kalam — fixed per-weekday segment lookup tables over the sunrise–sunset span). Global, not
  birth-dependent, computed from Sun/Moon sidereal longitudes at sunrise (not local midnight —
  matches how printed panchangs work) via `getTodaysPanchang(lat, lng, utcOffsetHours)`, which
  checks `panchang_daily` for today's row first and only computes+upserts if missing — reused
  everywhere "today's panchang" is needed rather than recomputed per request. Location-dependent
  (sunrise/sunset/kalam windows shift by place); defaults to the profile's birth-place
  coordinates, the only location this app currently tracks. All the underlying sunrise/sunset
  and "HH:MM local" ephemeris helpers are timezone-aware by construction (`julianDayLocalMidnightUt`,
  `jdToLocalHHMM`) — an earlier draft computed these in raw UT, which would have shown the wrong
  local day/hour for a sunrise near UTC midnight; caught and fixed before shipping.
- **Gochara** (transit analysis, `src/features/astrology/gochara.ts`) — for each planet's
  current sidereal position, computes house-from-Lagna and house-from-Moon relative to the
  natal chart (both are standard reference points; a first pass surfaces all current transits
  rather than scoring their significance, which `astrology.md` explicitly defers).
  Deterministic, no new ephemeris calls beyond the existing transit snapshot. Backend-only:
  feeds into the `astrology_reading` prompt context (dasha + gochara together, the standard
  "which life theme is active + how today's sky affects it" combination) and into
  `isChandrashtama()` below, but is **not rendered as its own UI element** — the persistent
  per-planet transit list that used to sit inside the Horoscope card was removed to match the
  current Claude Design source (pulled and matched 2026-08-15, which no longer shows it), and
  the now-unused `getCurrentGochara(profile)` wrapper action was deleted along with it (unlike
  Panchang below, `computeGochara`/`isChandrashtama` in `gochara.ts` itself still has real
  callers, so only the dedicated page-facing wrapper was removed, not the engine).
  `isChandrashtama()` is one dedicated flag on top of the same computed data: true when the
  transiting Moon's own gochara entry has `houseFromMoon === 8` — a lookup against data already
  computed, not a new formula, so it doesn't carry its own separate verification caveat the way

## 14. Prep (`/prep`) — v2.0, added 2026-09-24

The center of v2 (`ROADMAP-v2.md`): one place that answers *"what do I practice today, and am I getting interview-ready?"* for a Frontend Tech Lead / Senior UI role. Added after a usage audit found ~9 separate daily items (4–5 coding picks, a daily read, workout, metrics, expenses) and a September collapse in practice (coding 15/92, reads 1/20), with no behavioral, leadership, or system-design practice anywhere. Code in `src/features/prep/`; four tabs (`PageTabs`), deep-linkable via `?tab=today|questions|mock|stories` (`&cat=<category>` preselects a Questions category, `&format=screen|behavioral|system-design` a Mock Round format).

- **Today's Prep** (`plan.ts`, deterministic) — one sequenced ~45-min session per day, persisted in `prep_sessions` (one row per user+date, `blocks` jsonb) so the plan doesn't shift mid-day. Three blocks: **main practice** (25–40 min, by weekday focus) → **Concept** (10 min: 3 theory questions on the weakest area in the Question Bank — the daily-read option went with Learning and the Career topic quiz with the Interviews revamp, 2026-10-08) → **Leadership rep** (5 min: draft a story for the first uncovered competency, or rehearse one). Weekday focus: Sun Review & reset · Mon JavaScript & TypeScript depth (the active JS-function pick, else JS theory in the Question Bank) · Tue React & Next.js internals · Wed Frontend system design · Thu UI coding (the active UI-coding pick) · Fri Behavioral & leadership · Sat Mock round (a Frontend-screen Mock Round, block key `mock`, auto-ticks when a round is saved). Each block is ticked manually (`togglePrepBlock()`). A session is complete when every block is done (`completed_at`); the prep streak counts consecutive completed days (today given grace).
- **Job Hunt Mode** (`hunt.ts`, deterministic; v2.1, added 2026-10-03; adaptive since v3.2, 2026-10-07) — set in the Today tab's Job Hunt Mode strip: a target "interview-ready by" date + hours/day (`prep_settings`, one row per user; null `target_date` = off). When on, today's session is built by `buildHuntPlan()` instead of the weekday rotation: **one `bank:<category>` block per Question Bank category, weakest first** (sorted by `categoryGap()`, see War Mode below), with the daily **Mock round** (`mock` block; format by weekday via `mockFormatForDay()` — Sat system design, Tue/Thu behavioral, else Frontend screen; its minutes are the format's total; done at build time if a round was already saved today, else auto-ticks when one is saved) slotted third, then STAR stories (6%, the Story Bank) → Applications (10%, "3 targeted applications — or 2 + 2 referral asks — and follow up on anything older than 7 days"). Each category has a base share of the day and a per-question cost (Theory 17% / 4 min · AI-native 15% / 10 min · Behavioral Q&A 4% / 10 min · JS functions 15% / 25 min · UI coding 15% / 45 min · System design 10% / 60 min · Algorithms 3% / 30 min); **since v3.2 each share is multiplied by `0.5 + gap` (gap 0 = at its readiness gate, 1 = blind spot; `categoryWeights()`) and renormalized to the same total, and the quota is simply what fits in that time** (floor 1/day) — the old `min(capacity, ceil(unseen ÷ days left))` cap was dropped because on a long runway it left most of the day empty, and re-answering weak questions counts as practice. Block details name the weakest theory topic and the category's "% of gate". Projected "seen by target" = seen + quota × days. Saving or turning it off deletes today's `prep_sessions` row so the plan rebuilds. Bank blocks auto-tick when today's practiced count (Next in the Question Bank, or answered in a Mock Round) in that category reaches the quota (parsed from the label's "× N"); a session completes when every block is done, as before.
- **Question Bank** (Questions tab) — the full `coding_questions` pool (~1,126: theory "quiz" 324, AI-native 115, Behavioral Q&A 25, JS functions 196, UI coding 79, system design 40, algorithms 347) as a practice sprint. **No self-grading since 2026-10-07** (the Missed / Partial / Confident buttons were removed; a question is just practiced or not). Queue per category (+ optional topic filter): unseen first (by `sort_order` when set, else medium → easy → hard), then practiced ones longest-ago first. Each question: a typed answer prefilled with your last one, a word count, a link to the source (GreatFrontEnd) to check/solve — or, for **linkless Prep-added questions** (`url` null: all of AI-native and Behavioral Q&A, plus 41 theory, 20 UI coding and 20 system design added 2026-10-03 as `source = 'Prep additions'`), "Show key points / requirements / expected areas" (`answer_hints`). **AI review** (any question, ≥40 chars typed; `critiqueAnswer()`, below — returns `{rating, feedback}`: the prompt's first line is `Rating: N` on a 1–10 hiring bar (9–10 strong hire, 7–8 solid, 5–6 borderline, 3–4 weak, 1–2 no real answer), parsed off and shown as a colored badge (green 8+, amber 6–7, red below) above the feedback; the feedback isn't stored, the rating is saved with Next as `question_progress.last_rating`) → **Skip** (back of the queue for this visit, nothing saved) / **Next →** (`answerQuestion()` → `question_progress`: answer + attempts + `last_seen_at`, `status` left null). The category chips' "today" counts are derived from the bank's `last_seen_at` (IST today); the bank state lives in `PrepView` so Mock Round answers show up here without a reload. Practiced also includes questions completed in Coding (`coding_daily_questions.completed_at`; the newer of the two is `last_seen_at`). Coverage card: per-category seen/total + %, a single green bar, and in Job Hunt Mode the daily quota + projected coverage by the target date.

- **AI-native section** (`ai-native` category, v2.1, added 2026-10-03) — 115 open-ended questions for AI-native engineering interviews, prepared against the Apollo JD's bar (form your own hypotheses, pressure-test AI output, catch its mistakes, verify, own final quality). - **Interview Readiness matrix** (`readiness.ts`, deterministic) — 14 areas (`READINESS_AREAS` in `prep/types.ts`): JavaScript depth, TypeScript, React/Next.js, CSS & layout, Accessibility, Performance, Testing, Browser/network/security, Frontend system design, AI-native engineering, UI coding, **Algorithms (DSA)** (added v3.2: `Algorithms`/`Data Structures` topics + the `algorithm` category), Behavioral, Leadership. AI-native = that rating average once ≥2 are rated, else the share of the section practiced (coverage). Behavioral = Story Bank coverage blended with behavioral answer ratings; Leadership = Story Bank coverage (a competency counts when it has a story rated ≥3/5, weaker ones count half). `null` = no data ("blind spot"). - **Interview War Mode** (v3.2, added 2026-10-07; `war.ts`, `core.ts`, `coach.ts`, `forecast.ts`, `components/WarRoom.tsx`) — turns the Today tab into mission control: decide what to do → force it (focus timer) → measure it → find weaknesses → adapt tomorrow. copy never praises partial work. **Weekly forecast** (`generateForecast()`, `askAI('prep_forecast', …)`, Sonnet, 6h cache): "if you interviewed tomorrow" — likely strengths, up to 4 failures with why, the highest-risk question, 3 fixes — from readiness, blockers, weakest topics, mock reviews, focus time, revision queue, stories and active applications' JD priority topics; confidence = War readiness (not the AI's); stored in `prep_forecasts` (one per day); generated Sunday night by the coach cron or on demand. **Telegram Prep Coach** (Daily bot): 7:30am mission (`prep-coach-morning`, includes the next scheduled interview round from Interviews §3), 1pm behind-pace nudge only when ≥30 min behind (`prep-coach-midday`), 9:30pm day review + Sunday forecast (`prep-coach-evening`); bot commands START / PAUSE / DONE / STOP / "what now" drive the same focus sessions. - **Mock Round** (Mock Round tab, `mock.ts` deterministic + `MockTab.tsx`; added 2026-10-07, replacing Flashcards) — a timed interview simulation over the Question Bank. Three formats (`MOCK_FORMATS`): **Frontend screen** (6 questions, 38 min: theory on JS / React+Next.js / TypeScript / the weakest readiness areas' other topics at 6 min each, 1 AI-native at 8, 1 Behavioral Q&A at 6), **Behavioral round** (5 Behavioral Q&A at 4 min + 2 STAR prompts from `REHEARSAL_PROMPTS` at 5 min, competencies without a solid story first; 30 min), **System design** (1 question, 45 min, ones with requirements (`answer_hints`) first). Selection (`buildMockRound()`): per slot, unseen first (sort_order, then medium → easy → hard), then practiced longest-ago, skipping anything practiced today. Flow: one question at a time with a per-question countdown (amber under 1 min, red + "over time" past budget, never auto-advances), answer typed or out loud, **Skip** or **Next →**, no hints or links until the end. **Finish** saves the round immediately (`saveMockRound()`: each answered — not skipped — bank question goes into `question_progress` as practiced, a blank answer keeps the last typed one; a `mock_rounds` row; ticks today's `mock` block and any Job Hunt bank block whose quota is now met), then shows the round's **review** screen (`RoundDetail` in `MockHistory.tsx`): every answer next to its key points / reference link, and a single **AI review of this round** button (`reviewMockRound()` → `askAI('mock_round_review', ...)`, Haiku, uncached, one call for all answers — about $0.01 a round; enabled once any answer is typed). Per-answer AI review buttons were replaced by this on 2026-10-07. **Mock Interview Calendar** (`MockCalendar`, setup screen's right column): a month grid of every round (IST dates), a dot per round (filled = reviewed), month nav back to the first round; picking a day lists its rounds (format, time, minutes, answered/total, verdict or "Not reviewed yet"), and opening one shows its full `RoundDetail` — answers, key points and the stored review, or the review button if it never got one — full-width below. All rounds are loaded (up to 500). No grades and no score. An in-progress round is kept in localStorage (`prep-mock-round-v1`) so a reload or tab switch doesn't lose it. No AI unless a review is requested.
- **Flashcards — removed 2026-10-07.** The SM-2 flashcards (auto-created from missed Career/Learning quiz questions and partial/missed Question Bank grades) were mostly article trivia and answer-less backs, and duplicated the Question Bank's own review queue. `srs.ts`, the tab, the warm-up block and the quiz → card sync are gone; the `flashcards` table is kept but no longer read or written.
- **Prep feedback models** — all four Prep feedback tasks (`story_critique`, `ai_native_critique`, `answer_critique`, and since 2026-10-07 `mock_round_review`) use Haiku (the weekly `prep_forecast` uses Sonnet — one call a week) since 2026-10-03, so ~3× more critiques fit the low daily AI budget ($0.1667/day); prompts and response shapes are unchanged.
- **Story Bank** — STAR stories (`stories`: title, competencies[], situation/task/action/result, metrics, strength 1–5) tagged across 10 competencies (`COMPETENCIES`: Leadership — ownership, mentoring, influence, technical decision, raising the bar; Behavioral — conflict, ambiguity, failure, delivery under pressure, cross-team collaboration), shown as a coverage grid (✓ covered / ◐ draft / ○ none). **Rehearse** shows a static "Tell me about a time…" prompt for the chosen competency (`REHEARSAL_PROMPTS`, 5 per competency — 50, shuffleable), optionally linked to a story; the typed answer gets an AI critique (`rehearseStory()` → `askAI('story_critique', ...)`, Haiku, uncached — one of the module's two AI calls, with the AI-native feedback; fixed shape: Verdict / What worked / Fix next / Likely follow-up, under 180 words), saved to `story_rehearsals`.

## Architecture

**Thin page + feature view pattern:**

- `src/app/[route]/page.tsx` — async server component, fetches data, passes to view
- `src/features/[module]/components/[Module]View.tsx` — `'use client'` component, owns all interactivity
- `src/features/[module]/actions.ts` — `'use server'` functions (CRUD via Supabase)
- `src/features/[module]/types.ts` — TypeScript types for the module

**Optimistic UI:** mutations use `useOptimistic` + `useTransition` so the UI updates instantly before the server confirms.

**Supabase clients:**

- `src/lib/supabase/server.ts` — server components and server actions (cookies-based, RLS-scoped to the logged-in user)
- `src/lib/supabase/client.ts` — client components (browser)
- `src/lib/supabase/service.ts` — service-role client (used by cron jobs and the Telegram webhook — bypasses RLS since those code paths run without a browser session)
- `src/lib/supabase/middleware.ts` — session refresh + redirect logic, wired in root `src/middleware.ts` (matcher excludes `/api`, `_next/static`, `_next/image`, favicon, and image assets — so Telegram/cron webhooks are never gated by the browser auth check). Unauthenticated users on a page route are redirected to `/login`; authenticated users hitting `/login` are redirected to `/dashboard` (the landing page; was `/planner` until Planner was removed 2026-10-07).

**Loading / error states:**

- `src/app/[route]/loading.tsx` — per-route skeleton shown while the server fetches data (2026-09-24: every module route has its own, built from `PageSkeleton` in `components/Skeleton.tsx` with that page's real layout — chips, banner, stat-tile count, tabs, card rows with approximate heights — so content lands where the skeleton was instead of jumping out of one generic shape; the root `src/app/loading.tsx` generic `ModuleLoading` remains only as the fallback for routes without one)
- `src/app/[route]/error.tsx` — error boundary with a "Try again" reset button

**Shared components** (`src/components/`): `TopNav` (header + desktop nav + mobile bottom bar, combined), `ProfileMenu`, `Card` (`flex flex-col`, **no `h-full`** since 2026-09-24 — grid rows already stretch items to equal height by default, so rows meant to match (Coding's 4-card daily-pick row, Finance's By Category/Just Added) still do and can bottom-align actions with `mt-auto`, while `items-start` rows now size each card to its content; the old `h-full` default stretched short cards to their taller sibling even in `items-start` rows and had been patched per-card with `!h-auto`), `PageHeader` + `HeaderChip` (2026-09-24 — the one page header for every module: 34px/700 title with the design's -0.02em tracking, 11px pill chips with tones default/accent/good/warn/risk/accentSoft, optional right-side `action` and `subtitle`; replaced 10 hand-rolled header rows), `Modal` (generic modal shell — title/close/footer chrome + shared field style constants, used by all 10 data-entry modals across Career/Finance/Health/Coding/Learning/Settings), `ConfirmDialog` (built on `Modal` — title/description + Cancel/destructive-styled confirm button, gates every hard-delete action in the UI: Planner task, Career application, Finance loan/investment/goal/expense, Health workout, Learning resource, Settings reminder — each call site supplies its own item-specific description text), `EmptyState`, `Skeleton`, `AIAdvisorProvider`, `PageTabs` (added 2026-08-20 — a generic underline-style tab bar, `{key, label}[]` + active key + onChange, horizontally scrollable so it never breaks layout on narrow viewports; used by Career and Finance to split their 4+ sub-sections into tabs per the density rule below rather than one long vertical scroll).

**AI advisor header architecture** — every module's whole-page AI advisor (Career Mentor, Money Advisor, Health Coach, Code Mentor) lives in the top nav bar, not inline in page content. `TopNav.tsx` is a separate component from each page's `*View.tsx` in the layout tree and can't read a page's local state directly, so `AIAdvisorProvider` (wrapping the whole app in root `layout.tsx`) provides a shared registration slot: each View calls `useAIAdvisor(label, icon, content)` once, which registers the trigger's label/icon and portals `content` (real JSX from that View's own render, with full access to its local state) directly into the panel body DOM node via `createPortal` — content never round-trips through Context state, so typing/interacting inside the panel only re-renders the View itself, not the Provider (an earlier version that lifted content into Context state caused an infinite re-render loop; portaling was the fix). `TopNav.tsx` reads the currently-registered trigger via `useAIAdvisorTrigger()` and renders nothing on routes with no registered advisor (Settings). Not every AI feature moved here — only whole-page advisors did; per-item contextual AI (Career's bulk "AI Generate" interview questions, Learning's per-resource "Quiz me") stays inline, tied to whichever item is selected. Every advisor open (`AIAdvisorProvider`'s shared `toggle`) and every tab switch within a multi-tab advisor (Money Advisor, Health Coach, Study Coach, Ask Brain — each own their own local tab state, so each logs from its own tab-click handler) fires `logAdvisorUsage()` into `advisor_usage_log` (see Database) — Executive Summary logs from its own separate trigger too, despite bypassing the shared provider otherwise.

**Navigation structure** — a single `TopNav` component (not a desktop `Sidebar` + separate mobile `BottomNav` — an earlier PRD-v2 design called for pillar-grouped Learn/Build/Perform/Recover navigation in a collapsible sidebar, but the shipped nav is flat, ungrouped, and the same component handles both viewports). Desktop (`md:` and up) shows a flat row of 6 text-only nav pills (Dashboard, **Prep** (v2.0), Interviews, Finance, Health, Coding — Settings and Astrology both live in `ProfileMenu` instead, not top-level nav). Below `md:`, the same component instead renders a fixed bottom bar with 4 primary tabs (Home, Prep, Health, Finance — Prep replaced Planner 2026-09-24; Planner was removed entirely 2026-10-07) plus a "More" sheet for everything else (Career, Coding, Astrology, Settings — Astrology appears in both the mobile "More" sheet and the profile dropdown, same redundancy Settings already had). See "Navigation — TopNav" below for full detail.

## Database

Standard pattern: `user_id uuid references auth.users` + 4 RLS policies (select/insert/update/delete scoped to `auth.uid()`), except where noted.

**Schema-debt cleanup (2026-08-20):** this app previously had a policy of leaving orphaned tables/columns in place rather than migrating them away once a feature was removed — each individual call made sense at the time, but it accumulated into real cognitive load (every future reader had to re-learn which columns were dead). A single pass (`20260820b_schema_debt_cleanup.sql`, `20260820c_drop_interview_qa.sql`) dropped everything confirmed to have zero remaining code readers: the `goals`, `coding_quiz_attempts`, `resume_versions`, `trending_readings`, and `interview_qa` tables outright, plus `investments`' 4 SIP columns, `health_metrics.sleep_hours`/`water_ml`, and `health_profile.target_weight_kg`/`goal_deadline`. Two of these (`trending_readings`, `health_profile`'s two columns) still had live — if functionally pointless — reads/writes in `planner/actions.ts`, `telegram/handler.ts`, `health/actions.ts`, `health/types.ts`, and `HealthProfileForm.tsx`; those references were removed in the same change, before the drop. Going forward, the standing rule is: when a feature is fully removed, drop its schema in the same change rather than leaving it "for backward compatibility" — nothing in this single-user app's history has ever actually needed an orphaned column back.

### Deploying your own instance

[![Deploy with Vercel](https://vercel.com/button)](https://vercel.com/new/clone?repository-url=https://github.com/vinaysomawat/personal-ai-os&env=NEXT_PUBLIC_SUPABASE_URL,NEXT_PUBLIC_SUPABASE_ANON_KEY,SUPABASE_SERVICE_ROLE_KEY,ANTHROPIC_API_KEY,GROQ_API_KEY,CRON_SECRET&envDescription=See%20the%20README%27s%20%22Deploying%20your%20own%20instance%22%20section%20for%20where%20each%20value%20comes%20from&envLink=https://github.com/vinaysomawat/personal-ai-os%23deploying-your-own-instance)

This app is a single-user system — there's no way around some manual setup and a specific order of operations, since a few values (your own user ID, your own Telegram chat ID) don't exist until you've deployed once and signed up. Steps:

1. **Create a Supabase project** at [supabase.com](https://supabase.com) (free tier is enough). Get `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` from Project Settings → API.
2. **Run every file in `supabase/migrations/`** against that project, in filename order (Supabase Dashboard → SQL Editor, or the Supabase CLI).
3. **Get an Anthropic API key** at [console.anthropic.com](https://console.anthropic.com) (`ANTHROPIC_API_KEY`). Optionally get a Groq key at [console.groq.com](https://console.groq.com) (`GROQ_API_KEY`) — only needed for Telegram voice-note transcription; the app works without it.
4. **Generate `CRON_SECRET`** — any random string (e.g. `openssl rand -hex 32`).
5. **Deploy** — click the button above, or `vercel deploy`, setting the env vars from steps 1–4.
6. **Create your account, then lock signups down immediately — in that order, don't leave a gap.** The app has no invite gate of its own: by default the `/login` page's "Sign up" button lets anyone create an account against your database, and that window is open the moment your deployment is reachable. Two ways to close it:
   - **Safer — skip public signup entirely:** create your own (already-confirmed) user via Supabase Dashboard → Authentication → Users → "Add user", then log in directly at `/login` with that email/password. Public signup never needs to be enabled at all.
   - **Faster, if you're doing this in one sitting:** sign up normally at `https://<your-deployment>/login`, confirm your email, log in — then immediately go lock it down (next bullet) before doing anything else. Don't leave the tab open and come back to it later.
   Either way, then **lock down signups** in Supabase (Authentication → Sign In / Providers) — turn off the sign-up-enabled setting so `/login`'s "Sign up" button can no longer create new accounts.
7. Copy your user's UUID from Supabase Dashboard → Authentication → Users, and add it to your Vercel project's environment variables as `SUPABASE_USER_ID`, then redeploy — cron jobs and the Telegram bots use this to know whose data to act on.
8. *(Optional, for Telegram)* Create one bot per module you want via [@BotFather](https://t.me/BotFather), set the resulting `TELEGRAM_BOT_TOKEN_*` env vars, message any of your new bots once to learn your chat ID (e.g. via [@userinfobot](https://t.me/userinfobot)) and set `TELEGRAM_ALLOWED_CHAT_ID`, redeploy, then run:

   ```bash
   node scripts/setup-webhooks.mjs https://your-app.vercel.app
   ```

### Security model

This app assumes **exactly one user account per deployment.** Most tables enforce that with owner-scoped RLS (`auth.uid() = user_id`, the standard pattern this doc calls out at the top of the Database section) — but a handful of tables have no per-user concept at all, either because they're genuinely global/shared pools or system-level logs, and their RLS policies are scoped to *any authenticated user of this deployment*, not to a specific owner:

- `telegram_logs`, `panchang_daily`, `cron_runs` — system/cross-cutting logs with no natural single owner
- `workout_library`, `coding_questions`, `coding_tips`, `health_tips`, `learning_tips` (unused since 2026-10-08) — global curated content pools, no `user_id` column at all

For a true single-user deployment (the only configuration this app is built and tested for) this is correct and intentional — there's only ever one authenticated user, so "any authenticated user" and "the owner" are the same person. **If you fork this and ever add a second account to your deployment, audit these tables first** — a second account would be able to read all of them (though never any other user's owner-scoped data, like `tasks` or `expenses`, which stay properly isolated per-user regardless). This isn't a bug to fix; it's a deliberate simplification that only holds under the single-user assumption stated above.

**Shared primitives**:

- **Card** (`bg-surface-1 border border-surface-3 rounded-xl`, default `p-4` padding, usually overridden to `p-3.5`) — the base wrapper for nearly every widget on every page. Optional uppercase title row with a right-aligned `action` slot (a button, icon, or filter toggle).
- **EmptyState** — centered icon (slate-700) + message (slate-600) + optional accent CTA button with a `Plus` icon; a `compact` variant reduces vertical padding for use inside an already-titled Card.
- **StatCard** — the one stat tile for every page (restyled 2026-09-24 to the Claude Design tile: uppercase 11px label on top, 20px bold `tabular-nums` value, optional one-line `sub` detail, left-aligned; clickable variant with `active` border for Planner's filter tiles). Replaced five drifted variants — centered big-number tiles (Planner, Learning), local `StatTile` copies (Health, Prep), and inline markup (Finance's Portfolio/Total Debt/Net Worth, Coding's Streak/Solved/Completion) — and the migrated tiles gained sub-lines from already-fetched data (e.g. Coding Streak "best N days", Solved "E easy · M med · H hard", Health Calorie Target "Xg carbs · Yg fat").
- **FilterPill** — a toggle-button pill, inactive = `bg-surface-1 border-surface-3 text-slate-400`, active = `bg-accent text-white` (or a status-tinted color when used for status filters, e.g. Learning's Not Started/Completed pills).
- **InlineEdit** pattern (Finance) — a value renders as a plain button with a hover-revealed pencil icon; clicking swaps it for a focused text input + a green checkmark save button, Enter saves, Escape cancels. Used for salary, loan EMI/rate/months, investment amounts. Health's metric tiles use a simpler always-editable variant (bare `<input>` embedded in the tile, saves on blur/Enter, flashes a green checkmark on success) rather than a click-to-reveal step.
- **Skeleton loading states** — no spinners anywhere in the app; every loading state is `animate-pulse` gray bars (`bg-surface-2`) at varying widths, either a per-route `PageSkeleton` layout (route-level `loading.tsx` files) / the generic `ModuleLoading` fallback or a component-local 3–6-bar stack (AI panel responses, chart lazy-load placeholders).
- **Route-level error state** (`error.tsx`, identical on every page): centered `AlertCircle` icon (red, 60% opacity) + "Something went wrong" heading + a "Try again" button.

**Charts**: every chart in the app is `recharts`, always lazy-loaded via `next/dynamic({ ssr: false })` behind a pulsing placeholder block (never blocks initial page paint) — Dashboard's Life Score Trend, Health's Health Trend, Finance's Spending History (a bar chart + a category pie/legend). (Coding's Difficulty Progression chart was removed 2026-08-10, §7.) All colors/fonts/spacing are read from one shared config module, `src/lib/chart-theme.ts` (grid stroke, axis tick style, tooltip box class, and a 5-color chart palette on `--chart-1..5`), rather than repeated per component — built during a 2026-08-10 chart-fidelity pass against the design's actual chart markup (`audit/CHARTS-AUDIT.md` has the full per-property audit). Key specifics per chart, since the design turned out to specify real per-chart behavior rather than one shared recipe:

- **Life Score Trend** — an `AreaChart` (line + `var(--accent-soft)` fill, not a bare line), `type="linear"` (straight segments, not smoothed), a **dynamic Y domain** (the series' own min/max with a small padding margin, not a fixed 0–100 scale, so a narrow score range still fills the chart height instead of flattening near the middle), 3 fixed `ReferenceLine`s at the domain's min/mid/max standing in for gridlines, and **persistent point dots in Weekly view only** (Monthly shows none) — matching the design's own `isTrendWeekly`-gated dot rendering exactly, not a hover-only `activeDot`.
- **Spending History bar chart** — no gridlines, no axis line, an explicit `domain={[0, 'dataMax']}` (bars scale to the exact 12-month max, no recharts "nice number" headroom), all 12 month labels shown (not every-other).
- **Spending History pie** — a **solid pie, no donut hole** (`innerRadius={0}`) and `paddingAngle={0}` (segments are contiguous, no gaps) — matches the design's literal `conic-gradient` circle. Category colors are a fixed 5-name lookup (`Housing`/`Bills`/`Transport`/`Food`/`Entertainment` → `--chart-1..5`, the design's own mapping) with every other category falling back to `var(--border-strong)`, not the old per-category rainbow of hardcoded hex.
- **Health Trend** has no design counterpart at all (the design's Health screen has zero chart markup) — kept as real functionality beyond the mock, `type="monotone"` unchanged, just repainted to read its grid/axis/tooltip colors and its 4 metric-series colors from the shared theme module instead of hardcoded hex that silently broke in light theme.
- Tooltips are real interactivity kept on every chart despite the static design mock showing no hover state at all for any of them (same "real functionality beyond a static mock" precedent used throughout this project's other audits).

The two ring/gauge visualizations (Dashboard's big Life Score ring, Health's Health Score ring, and every small `MiniRing`) are hand-drawn SVG with a purple→cyan or green→cyan gradient stroke, not recharts.

**Iconography**: `lucide-react` throughout, no other icon set — with one deliberate exception: Astrology uses the 🔮 emoji everywhere it's referenced (Dashboard strip, Bot Activity rows, Telegram replies) rather than a `lucide-react` icon, since a crystal-ball glyph reads more immediately as "astrology" than any available line icon and the emoji was already established across the module before this doc was audited; not a gap to silently fix by swapping it for a lucide icon. Sizes are almost always 11–16px inline with text, 18–32px for empty-state/placeholder icons. Module-to-icon mapping is consistent everywhere a module is referenced (nav, Bot Activity rows, reminders): Prep `Target`, Career `Briefcase`, Finance `DollarSign`, Health `HeartPulse`, Learning `BookOpen`, Coding `Code2`, Dashboard `LayoutDashboard`, Settings `Settings`, Astrology 🔮 (emoji, see above).

**Currency/number formatting**: ₹ amounts use `Intl.NumberFormat('en-IN', { style: 'currency', currency: 'INR', maximumFractionDigits: 0 })` (Indian digit grouping, e.g. `₹1,20,000`, no decimals) everywhere in Finance/Dashboard. AI spend (`$`) formats to 4 decimals when under a cent, else 2. Numbers that update live (scores, counters) use `tabular-nums` so digits don't jitter horizontally as they change.
