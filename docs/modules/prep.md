# Prep (`/prep`)

The center of the app: *what do I practice today, and am I interview-ready?* for Senior Frontend / AI Product Engineer roles. Code in `src/features/prep/`. `loadPrepData(db, userId)` (`core.ts`, a plain server module, not `'use server'`) is the one data path for the page, the crons and the Telegram bot. It runs all its reads in one parallel round (settings and the question bank included); the **global question pool** (`coding_questions`, ~1,200 rows, no user_id) is cached for an hour across requests (`unstable_cache`, tag `question-pool`; pages read two at a time when cold), so a re-seed shows up within the hour — your own progress (`question_progress`) is read fresh every time. Tabs (`PageTabs`): **Today / Interview / Questions / Mock Round / Story Bank**, deep-linkable via `?tab=` (`today` / `ai` / `questions` / `mock` / `stories`), `&cat=<category>`, `&topic=`, `&format=screen|behavioral|system-design|machine-coding|code-review|ai-system-design`.

## Interview War Mode and the day plan

- **Always on.** There is no off switch; `isHuntMode()` (`hunt.ts`) returns true and stays the one shared check. There are no load levels and no rest day: the day template sets the day.
- **Day template** (`dayplan.ts` `DayTemplate`, stored in `prep_settings.day_template`, null = `DEFAULT_TEMPLATE`; `templateOf()` fills missing pieces): **sessions** — Morning (start → 1:00pm), Library (2:30pm → 9:30pm), Late (10:30pm → 12:30am); **gaps** between them — "🍽️ Lunch" (1:00–2:30pm), "🍽️ Dinner + walk" (9:30–10:30pm); and **minutes per day** per plan key (`minutes`, the same every day; a template saved with per-weekday minutes reads as each slot's highest value). There are no automatic breaks — you add breaks for a day in Edit today. The day starts at `prep_settings.day_start_min` (default 11:00am, after the gym); **only the first session moves** with it. **The Prep day rolls over at 04:00 IST, not midnight** (`prepToday()` / `toPrepDateStr()` / `prepDaysAgo()` / `prepDayStartUtc()` in `src/lib/date.ts`, `PREP_DAY_ROLLOVER_HOUR`): everything in Prep — the plan, block ticks, "answered today", focus time, streak, pace, mock-round days — and the Dashboard's Prep items use the prep date, so work at 12:30am still counts for the day it started. The rest of the app keeps the IST calendar day. `isHuntMode()` is the shared check — code identifiers (`hunt.ts`, `isHuntMode`, `HuntHero`) keep the older "hunt" name; every user-facing string says Interview War Mode.
- **Recommended plan** (`planItems()`), stored once per day in `prep_sessions.blocks` (focus "Today"): the template's keys in `ORDER` with their minutes, each built by `blockFor()`; the mock only on its scheduled days. **Rotation, least-covered first** (`rotate()`): the talk-through question blocks (`TALK`: System design, FE architecture & lead, AI engineering, Backend & APIs, From my resume, AI-native, Theory, Angular, Behavioral Q&A), sorted by coverage (practised ÷ total in the category, ascending; ties keep `ORDER`), alternate with everything else. Everything else means the hands-on question blocks (UI coding, Algorithms, JS functions, Code review, also sorted by coverage among themselves), the mock, Job applications and your own slots, so you never do two talk-through blocks in a row. Talk blocks left over once the others run out go at the end. **Speak later in the day** (`speakLate()`): every talk-through block planned to start 3h or more into the day (`SPEAK_AFTER` = 180 min, counted over the plan's minutes) has its detail start with "🎙 Speak these — or text the Daily bot \"drill {word}\" and answer on a walk." (`DRILL_WORD`, matching the drill aliases). Default minutes a day (≈ 5h = 285 min, + the mock on its days; real output fades after about four hours, so the default is a day you can finish): five talk-through blocks against four changes of mode. Talk-through: Frontend system design 60 · FE architecture & lead 30 · **AI engineering 30** · Backend & APIs 30 · From my resume 30. Changes of mode: UI coding 45 · Code review 30 · **💼 Job applications 30** (`apply`, no questions — done by FocusBar Finish) · the scheduled mock. Algorithms, JS functions, Theory, AI-native, Angular and Behavioral Q&A are off the default plan; they stay in the bank and can be added in Default plan or Edit today. The **AI engineering path** has no tab and no plan blocks: `/prep?tab=ai` still opens it with your ticks, older days keep their Learn and Build slots, and AI engineering is practised through its Question Bank category (`roadmap.ts`: `ROADMAP`, 11 weeks of 7 days counted from `BUILD_START` = 2026-10-16, so W4 starts 2026-11-06 and the RAG weeks come first (W4 and W5 don't depend on W2 or W3, which stay open); `roadmapWeek()` is null before the start and after the last week), the route from Senior Frontend → full stack → AI engineer. Everything is built in **Job Copilot** (`PROJECT`), a small fresh repo you write yourself, not Personal OS: paste a job description → it pulls out the skills, matches them to your notes, answers questions about your prep with citations, and later an agent tracks your applications. Four stages (`STAGES`): **1 LLM apps in TypeScript** — W1 your first LLM call (tokens, Messages API, system prompt, temperature, server-side key), W2 streaming & structured output (zod), W3 Postgres + RLS · **2 Retrieval** — W4 embeddings (pgvector), W5 RAG with citations, W6 hybrid search + the first eval (recall@5) · **3 Agents & MCP** — W7 tool calling written by hand, W8 agent UX + human-in-the-loop, W9 an MCP server · **4 Ship** — W10 Python + FastAPI, W11 evals, tracing, safety, fallbacks and packaging. Each week has a goal, 3–5 **concepts** in plain words, **5 steps** (`RoadmapStep`: title, task, "done when" check, the concept it needs), links, an **interview line**, and a **theme** (`theme`: the bank category + topics for the drill; W3 = Backend Row Level Security + Data, W10 = Backend FastAPI, the rest AI engineering). Steps are ticked in the AI Engineer tab (`roadmap_steps`, `setRoadmapStep()`); `nextStep()` = the week's first unticked step. **Learn** (`learnBlock()`) is that step's concept with its plain explanation and the week's links; **Build** (`buildBlock()`) is that step's task and done check ("Build · W{n} step {i}/5: …"), or "write it up" once all 5 are ticked. Ticking a step also re-points today's stored Learn / Build blocks at the new next step (minutes and done kept).
- **Mock schedule** (`mockFormatForDay()`, `mock.ts`): Sun frontend screen · Tue behavioral · Thu frontend system design · Sat machine coding; Mon / Wed / Fri none. AI system design stays a format you can pick in Mock Round.
- **On the clock** (`layoutDay(items, template, start, interview, breaks)`): the sessions minus fixed events (the interviews with their warm-ups and debriefs, your breaks) give free stretches; each stretch takes the **first items in order that fit** (a shorter later item fills a gap a longer one can't, so the order moves only as much as needed); whatever is left in a stretch (≥10 min) is **Flex** ("finish any open block, or redo weak answers"); items that fit nowhere come back as `dropped` (shown as "Doesn't fit today"). **Job applications** of 20 minutes or more are planned as two slots: half in the normal flow, and the rest as `apply~2` (`NIGHT_SLOT`), which opens the day's last session. If that session has no room, for example because of an interview, `apply~2` flows like any other item. A split made in Edit today uses the same key, so its second slot also goes to the last session. `ORDER` is quick, sharp work first (morning), deep work at the library, lighter spoken work late — and the later a key, the sooner it gives way on a short day.
- **Interviews today** (`prep_sessions.interview`, a list of `{start, minutes, label}`, up to 5, `MAX_INTERVIEWS`; days saved earlier hold one object, so read it through `interviewsOf()`): a 30-min **warm-up** before and a 15-min **debrief** after each (`WARMUP_MINUTES`, `DEBRIEF_MINUTES`) are cut out of the sessions. In a gap between two interviews the debrief comes first and the next warm-up gets what's left, so 20 minutes gives 15 + 5; under 10 minutes (`MIN_INTERVIEW_GAP`) the gap gets neither. Overlapping interviews can't be saved. If the first warm-up is before the day's start, the day starts then (gym skipped). Items that no longer fit drop from the end of `ORDER`. Every interview prep for today with a time joins the list (`addInterview()`, which replaces one at the same start and ignores a sixth), and today's question blocks put the categories from all of today's preps first (`prepCategories()`).
- **Editing** (nothing saves until Save): **Edit today** (`EditToday` in `DayEditor.tsx` → `savePrepToday()`) — today's start (`prep_sessions.start_min`), the interviews (add, change or remove each), **today's meals** (each template gap — lunch, dinner — with its own start, end and name for today; stored in `prep_sessions.breaks` as `{start, end, label, meal: <gap index>}` only when it differs from the default plan, `mealsOf()`; `layoutDay()` ends the session before it at its start and starts the next at its end), **your breaks** (`prep_sessions.breaks`: start and end time + an optional name, up to 10, each ≤ 4h; fixed on the timeline, blocks flow around them), and the items: reorder (drag a slot by its ⠿ handle — pointer events, so touch works; ↑ / ↓ on the focused handle), change minutes (5–300; the mock keeps its format's), remove, **split** (✂ halves a slot into two of the same item, e.g. 60 → 30 + 30, then move / resize each), add any plan key — again as another slot if it's already there (not the mock) — or **your own slot** (`custom:<id>`, a name + minutes, done by FocusBar Finish). **Several slots of one item**: the first keeps the plan key, the rest are `<key>~<n>` (`baseKey()` / `catOf()` in `hunt.ts` strip it; `blockFor()` builds them like the item and keeps the key); each has its own minutes, place, timer and tick, an added slot keeps the minutes you set, and the default plan stays one entry per item (Job applications splits only when the day is planned, see On the clock); a live preview shows the laid-out day and what doesn't fit; Save sends **only what changed** (`diffToday()` → `TodayPatch`: start, interview, breaks, removed / added slots, changed minutes or names, and the full order only when something moved); the page applies it at once with the same `applyTodayPatch()` the server uses and closes the editor, then `savePrepToday(patch)` → `patchToday()` saves it behind in one read and one write of only the changed columns, re-checking progress only for question blocks that were added or resized (a failed save restores the day and reopens the editor with the error). Existing items keep their state. **Default plan** (`EditDefaultPlan` → `savePrepTemplate()`) — session names and times (the first's start = the default day start), gap labels, and **minutes per day** for each plan key (one value, the same every day; the mock an on/off for its Sun / Tue / Thu / Sat; the total in red when over the sessions' time); it applies from the next day's plan, while today's times re-lay with the new sessions and breaks.
- **Question blocks are time boxes**: a block's minutes (rounded to 5, at least one question's worth) are its target, and the question count in its detail ("about N") is only a guide = minutes ÷ the category's minutes per question (`BANK_CATEGORIES`: UI coding 45 · System design 60 · Theory 5 · Backend & APIs 8 · JS functions 25 · AI-native 10 · Algorithms 30 · Angular 6 · Behavioral Q&A 10 · Code review 15 · From my resume 8 · FE architecture & lead 8 · AI engineering 8), at least 1. Categories with no block that day have no planned minutes (still free to practise); the Questions tab's per-category planned minutes, done ✓ and guide count (which sizes redo slots) are read live from today's plan blocks (a category's slots summed), so they match the timeline and follow Edit today. Behavioral Q&A, Angular and other unplanned categories are practised through mocks, Telegram drills or by choice. **Redo weak answers** (`isRedoDue()` / `redoSlots()` in `hunt.ts`): a question whose latest rating is under 7 is due again 1 day (<5), 2 days (<6) or 4 days (<7) after that rating — the revision queue's gaps (`redoInterval()`), and not if already answered today. Up to 40% of a block's quota (`REDO_SHARE`, rounded — so a quota of 1 has none) is redo slots: the day's first answers in that category go to due weak answers, the rest to new questions; a redo replaces the old rating, and at 7+ the question stops coming back. `bankCoverage()` counts `redoDue` per category, and the plan block's detail says "the first N redo your weak answers"; the answer panel's header reads "Redo · was N/10 on MM-DD". **Block progress** (`blockProgress()`, `war.ts`) = the larger of the minutes focused on the block today (`focusedMinutes()` over `prep_focus_sessions`) and today's answers in its category × its minutes per question, capped at the block's minutes; slots of one category share its answers in day order (`ProgressCtx.order` — the earlier slot fills first, the next gets the rest) — so Telegram drills and Mock Round answers count without the timer. A question block auto-ticks when progress reaches its minutes (`blockReached()`; `syncBankBlocks()` after every answer, drill, mock save and focus stop; the page also finishes the running session on the minute tick once its time is reached); the mock block when a round is saved.
- **Prep streak** = consecutive days with a completed session (today given grace; `prepStreak()`, also on the Dashboard).

- **Learn bar** (`TopicLinks.tsx`, data in `topic-links.ts`, no AI): under each question's title, up to 3 of its topics, each with links that open in a new tab: docs or a website, an article, and a YouTube video or search. Links are per topic, and topics sharing the same links show once. A question with no linkable topic falls back to its category's links (JS functions, UI coding, AI-native, Angular). - Each question: a typed answer — prefilled with your last answer only if you answered it today (a repeat on a later day starts blank), word count. **AI review is mandatory before Next** for any answer of ≥40 chars: the primary button reads **Review** until the review lands, then **Next →**. Shorter answers (e.g. a note on a problem solved on the linked site) go straight to Next. An empty box shows **Skip →** instead (secondary style, hint "Nothing typed — Skip won't count it"): it moves to the next question without saving — no `last_seen_at`, no quota credit, the question stays unanswered. Editing after a review dims it with a **Re-review edited answer** link; Next stays available. A failed or budget-fallback review still unlocks Next. Review = `critiqueAnswer(id, answer, spoken)` → `critiqueQuestion()` in `critique.ts`: `ai_native_critique` for AI-native, otherwise `answer_critique`; Haiku 5.5 at low effort, uncached; rubric by category (`rubricFor()`): `technical` for theory/Angular/UI coding/system design/algorithms/backend, `behavioral`, `ai-native`, `code-review` (the diff is included in the prompt). An answer dictated with Speak gets `SPOKEN_NOTE` (ignore transcription errors, judge as spoken). **The AI only judges; code scores.** It returns a JSON scorecard (`Scorecard`, `scorecard.ts`): `points` (the question's `answer_hints` split into key points, or 4–6 it derives when none) each `covered` / `partial` / `missing` with a note; `correctness` 0–2, `depth` 0–2, `clarity` 0–1 (labels per rubric — behavioral: No red flags / Evidence / Direct & concise; AI-native: Judgment / Real example / Clarity); `summary`, 2–3 `fixes`, `followUp`. **Rating** (`scoreCard()`): coverage = (covered + ½·partial) ÷ points, substance = min(1, 2·coverage); rating = round(1 + 9·(0.55·coverage + substance·(0.25·correctness/2 + 0.08·clarity) + 0.12·depth/2)), capped at 4 on correctness 0 and at 5 when coverage < ⅓, clamped 1–10. Verdict from the rating: ≥8 Strong, ≥6 Good, else Needs work. The `AnswerReview` card: rating chip + verdict + summary, a breakdown line (Key points c/n · the three criteria), the key-point checklist (✓ / ◐ / ✗ + note, two columns on `sm+`), numbered Fix next, Follow-up callout, `code` as monospace chips. A reply that isn't a valid scorecard (budget fallback, malformed JSON) shows as plain text with no rating. **Answer** (not on algorithm / JS functions / UI coding, which keep "Open the problem"): `revealModelAnswer()` → `modelAnswer()` (`model_answer`, Sonnet, cached 1 year — the prompt is fixed per question, so only the first reveal costs): a 150–220-word spoken-style model answer covering the key points (theory: what → how under the hood → example → trade-off; system design: compact outline; behavioral / AI-native: an example labelled "adapt it to your own experience"), current as of React 19 / Next.js 15 / Angular 19, fenced code rendered as code blocks. Revealing it **before** any review marks the attempt *studied*: the Review gate lifts, the panel says "won't be rated", and Next saves no rating (`last_seen_at` still updates). Revealing after a review changes nothing. **Answer follow-up →** under the review card's follow-up (Question Bank and Story Bank): your own answer + 🎙 Speak → `critiqueFollowUpAnswer()` → `critiqueFollowUp()`, the same scorecard with derived key points (story follow-ups use the behavioral rubric), shown as a nested review card; practice only — nothing stored, the original rating untouched. **Next →** (`answerQuestion()` → `question_progress`: answer, attempts, `last_seen_at`, and the rating as `last_rating` / `last_rated_at`) moves to the question below in the list.
- **Time left** (`minutesPerQ` from `BANK_CATEGORIES`): unseen questions × the category's minutes per question, shown in whole hours rounded up (`Math.ceil`). The Sprint header reads `N answered today · {planned} planned · N questions · ≈ Xh to complete`, and the Coverage card shows `≈ Xh` on each category row and the all-category total in its header.
- Coverage card: per-category seen/total · % · ≈ hours to complete, and today's planned minutes (green with ✓ once the block is done); header = overall % (bold, accent color) · seen/total · ≈ total hours, with an overall accent progress bar above the green per-category bars.

## Voice mode (web)

## Readiness, War Mode and revision

- **Readiness matrix** (`readiness.ts`, 17 areas in `READINESS_AREAS`): JS, TS, React/Next.js, CSS, Accessibility (its topic counts rated answers), Performance, Testing (also fed by `code-review` ratings), Browser/network/security, System design (also fed by `architecture` ratings), AI-native, UI coding, Backend & APIs (the `backend` category + the Networking & APIs topic), AI-assisted coding (`code-review` ratings — reviewing AI-generated PRs), AI engineering (`ai-engineering` ratings — RAG, vector DBs, agents, HITL, evals), Algorithms, Behavioral, Leadership. Each averages real signal: AI answer ratings ×10 on the area's topics/category (≥2), coding outcomes from older practice history (solved 100 / with help 60 / struggled 30). Samples under 5 are shrunk (`score × n/5`). Behavioral blends Story Bank coverage with `behavioral` and `resume` ratings; Leadership blends Story Bank coverage with ratings on Tech-lead `architecture` questions. Angular is not an area (the role target is framework-agnostic; the `angular` category stays in the Question Bank for practice). `null` = blind spot.
- **Gates** (`GATES` in `war.ts`, weights follow the day split — frontend areas weigh most: React and UI coding 12, System design 15): JS 80 · TS 75 · React 80 · CSS 70 · A11y 70 · Perf 75 · Testing 70 · Browser 75 · System design 80 · AI-native 75 · UI coding 80 · Backend & APIs 60 (weight 5) · AI-assisted coding 75 (weight 8) · AI engineering 70 (weight 10) · DSA 70 · Behavioral 80 · Leadership 75, plus mock average (last 5 reviewed rounds) ≥ 8/10. `warReadiness()`: overall = weighted average (blind spots = 0) × `(0.5 + 0.5 × lowest/100)`; blockers = everything under its gate, biggest gap first.
- **Tiers** (`readinessTier()`): 🔥 TOP 1% READY (no blockers) → ✅ INTERVIEW-READY (overall ≥60, no blind spot, and mock average ≥7) → 🧭 Building (everything below that — the normal state for most of a prep arc, not a failing grade).
- **Topic weakness** (`topicWeakness()`): struggle rate ×40 + (1 − avg rating/10) ×25 + days idle (/14, capped) ×15 + interview importance ×20.
- **Revision queue** (`revisionQueue()`): a topic whose rated answers average under 7 comes back after 1 day (<5), 2 (<6) or 4 (<7); overdue/today 🔴, tomorrow 🟠, later 🟡.
- **Focus sessions** (`prep_focus_sessions`): Start on a block starts the timer and jumps straight to the block's work (its in-page `href`: Questions category, Mock format, Stories). No separate screen: the timer is a floating **FocusBar** (bottom centre, above the mobile nav): label (tap = go to the work) · on `bank:` blocks "{progress}/{minutes}m · N answered" · countdown (bar turns red past the plan) · Pause (+1 interruption) / Finish (ticks the block; on a `bank:` block disabled until progress reaches 80% of its minutes, `FINISH_SHARE` / `canFinishBlock()`) / Stop (keeps the time; a `bank:` block whose time is then reached ticks). `endFocus(finished)` under 80% refuses (`bankShortfall()`, `core.ts` — the session keeps running; Telegram "done" replies "{progress}/{minutes} min — it ticks itself at {minutes}, and DONE works from {80%}"). Mission rows have no checkbox — a read-only status circle (✓ when done; tooltip "Completes at {minutes} of practice" on open bank blocks). Blocks complete only from the work: a question block's minutes reached (or Finish from 80%), Mock Round saved, or FocusBar Finish (Learn, Build). While focusing, the Mission button reads "Go to work". **Auto-stop:** `updateBlocks()` completes the active session the moment its block turns done from any path (minutes reached by answers, a Telegram drill, a Mock Round or focus time, or a block finished from the FocusBar); the page mirrors it locally and the bar shows "✓ <block> done · m:ss focused" for 5 s. On a question block it adds a second line for 8 s, built from the bank as the page has it (`focusWin()` in `PrepView.tsx`, no AI): "+N answered · avg R · {Category} x% → y%". N is the answers since the session started, avg is their ratings, and the coverage before → after uses a snapshot taken at Start; after a reload only the current % shows. One active session, shared with Telegram. Focus time is not a scored measure. **Pace** (`dayPace()`, `war.ts`): the window is today's timeline, first slot to last (`windowOf(rows)`, read in prep hours: after midnight they keep counting past 24, so 1am = 25, via `prepHourNow()`). Work done = Σ(block minutes × progress) ÷ planned minutes, where a `bank:` block's progress is `blockProgress()` ÷ its minutes (focus time or `practicedToday()` answers × minutes per question) and other blocks are 0 or 1. Time used = share of the window gone. `deltaMinutes` = (done − time used) × the window's minutes; within ±10 min = On pace, else **Ahead / Behind Xh Ym** (`paceStatus()`, `paceLabel()`). `coachLine(pace, nextBlock, good)` names what got done first, then the single next step — "3/12 blocks done. Next: <block>." (none done yet: "Start with <block>."; after 19:00: "N/M blocks done."; all done: "All N blocks done — a good day ✓"); factual, no guilt wording, shown in a neutral tone (green on a good day). **Good day** (`isGoodDay()`, `war.ts`) = 3 blocks done (`GOOD_DAY_BLOCKS`), whatever the % — a ✓ in the evening review, the War header line and the Hunt Hero score. Mission block rows show "{progress}/{minutes} · N answered" on unfinished bank blocks. **Speed:** the web timer is optimistic — Start shows the bar at once with a local session (Pause / Finish / Stop wait only while that first save is in flight), Pause / Finish / Stop update the page immediately, and the server call runs behind it; none of the timer actions revalidate the page (`startFocusSession(block)` → `startFocusOn()`: the running session or one insert; `endFocusSession()` → `endFocus(…, verified)` skips re-reading progress the page already checked with `canFinishBlock()`, and `updateBlocks(…, closeActive=false)` skips re-closing it). Telegram start / done use the full checks.
- **Timeline** (`timeline.ts`, `TimelineCard.tsx`, deterministic, client-safe): today's laid-out day (`layoutDay()`, computed on the page from the stored items, start and interview) re-flowed every minute by `liveTimeline()`: rows that ended stay put; blocks not done in their slot move to now (marked "moved"); **fixed-time rows** — meals, your breaks, the interviews with their warm-ups and debriefs — keep their place and blocks / breaks / Flex flow around them (`fitAt()`); a block or Flex in progress gives way to any missed blocks, so "now" is the earliest undone work; Flex shrinks first; anything past the planned end shows as "N min over" (`overHint()`). Times are prep minutes; `clock()` formats them ("12:30am").

## Interview prep from a job description (Interview tab)

For a specific upcoming interview: paste the JD with the company, role, round, date, time (IST) and length → `createInterviewPrep()` (`actions.ts`) saves an `interview_preps` row with three layers:
- **Match (deterministic, `jd.ts` `matchJD()`, no AI)**: the JD's skills from a keyword dictionary (`SKILLS`: React, Next.js, JS, TS, CSS, performance, a11y, testing, APIs, Node, Python, databases, caching, auth, system design, FE architecture, build tooling, real-time, Angular, LLMs, RAG, agents, evals, AI-assisted coding, DSA, machine coding, code review, leadership — each mapped to Question Bank categories/topics), the matched categories strongest first, your coverage per category (% practised, average rating), up to 24 **bank questions to practise** (per matched topic: weak answers < 7 first, then unseen, then longest ago; each opens the Questions tab on its category/topic), and the **stories to have ready** (Story Bank stories whose competencies the JD's wording hits, strongest first).
- **AI plan** (`interview_plan`, Haiku 5.5 at low effort): role read, 4–6 focus areas, likely rounds, 14–18 likely questions tied to JD lines, what the company is known to ask (model knowledge, labelled as possibly dated), questions to ask them, what to prepare for, and a timeline from now to the interview. A budget or parse failure saves the prep without a plan and offers Retry (`retryInterviewPlan()`).
- **Online research** (`research`): written by the **`/interview-prep` Claude Code skill** (`.claude/skills/interview-prep/`), which searches the web on the user's Claude plan (not the app's AI budget — live web search stays out of the gateway), extracts the reported process, most-asked questions (with counts and sources) and sources with dates, and PATCHes them onto the prep. Without it the card shows Google searches restricted to the last 12 months (`searchLinks()`: Glassdoor, AmbitionBox, LeetCode Discuss, Reddit, GeeksforGeeks, Blind, LinkedIn posts).

**Day plan**: a prep for today immediately joins today's interviews (`interviewOf()`: its time and length, label "company · round", so the timeline adds the warm-up and debrief) and moves the matched categories of all today's preps to the first open question-block slots of their kind, talk-through or hands-on, so the rotation holds (`frontLoad()` in `dayplan.ts`); a prep for a later day is applied the same way when that day's plan is first built (`loadPrepData()`).

## Mock Round

`mock.ts` + `MockTab.tsx`. Stored in `mock_rounds.review` (`review.score` = average rating, computed in code) and the ratings written to `question_progress`. **Mock Interview Calendar** lists every round by day with its review and ratings (no answers; an unreviewed round can't be reviewed from there). An in-progress round survives reloads (localStorage `prep-mock-round-v1`).

## Voice drill (Telegram)

`drill.ts`.
